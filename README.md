# ContextFlow

업무 맥락 유지 및 지식 관리 도구 (Windows Desktop · Tauri 2.0)

여러 업무를 오가며 생기는 맥락 손실을 줄이는 것이 목적이다. 왼쪽에서 업무를 고르면
그 업무 전용 작업공간(파일 탐색기 · 에디터 · 마크다운 뷰어 · 메모장)이 그대로 복원되고,
모든 데이터는 Obsidian Vault 폴더 구조로 저장되므로 완료된 업무를 Obsidian에서 바로 열 수 있다.

UI는 `design/ContextFlow.dc.html`(Claude Design 프로젝트에서 내려받은 원본)을 그대로 옮긴 것이다.
폰트 · 글자 크기 · 창 바깥 여백만 의도적으로 다르며, 이유는 아래 "알려진 제약"에 적어 두었다.
`design/support.js`는 디자인 미리보기용 React 런타임이며 앱에서는 사용하지 않는다.

## 실행

```bash
pnpm install
pnpm tauri dev        # 개발 실행
pnpm tauri build      # msi / nsis 패키징
```

검증:

```bash
pnpm typecheck                                   # TypeScript
pnpm test                                        # Vitest (마크다운 파서 · 이미지 · 줄 편집 · 파일 트리 · 오늘의 한일 · 탭 닫기 · 편입/분할 · AI 실행 · 기능별 연결 · 위키 파서/큐/자동 반영 · 위키 대화 · 웹 검색 진행)
cargo test --manifest-path src-tauri/Cargo.toml  # Rust (frontmatter · Vault 생애주기 · 편입/분할 · 파일 조작 · 추천 · 기록 저장소 · SSE · FabriX · 위키 저장소 · 웹 검색 브라우저)
pnpm build                                       # 타입 검사 + 번들
```

웹 검색 브라우저(`browser.rs`)를 실제 브라우저로 돌려 보려면 실행 파일을 알려 준다 — 로컬 HTTP 서버에 띄운
결과 페이지 · 본문 페이지로 조종 · 추출 · 재사용 · 종료를 확인한다. 없으면 그 테스트는 건너뛴다. 실제 검색
엔진으로 확인하는 테스트는 네트워크가 필요해 기본으로 돌지 않는다(`--ignored`).

```bash
CONTEXTFLOW_TEST_BROWSER="C:/Program Files/Google/Chrome/Application/chrome.exe" cargo test --manifest-path src-tauri/Cargo.toml browser
CONTEXTFLOW_TEST_BROWSER=… cargo test --manifest-path src-tauri/Cargo.toml live_engines -- --ignored --nocapture
```

## 저장소 구조 (Obsidian Vault)

진실의 원천은 파일시스템이다. 업무 메타데이터는 `index.md`의 YAML frontmatter에 있고
별도 DB가 없다. Obsidian에서 보이는 것이 곧 ContextFlow에서 보이는 것이다.

예외는 하나, **오늘의 한일**이다. 그것만 Vault 밖 SQLite(`~/.contextflow/today.db`)에 산다 —
날짜를 축으로 한 교차 기록이라 어느 한 업무의 frontmatter에 넣을 자리가 없다. 이유는 아래
"오늘의 한일"에 적어 두었다.

```
%USERPROFILE%\Documents\ContextFlow Vault\   ← 설정에서 변경 가능
├── Tasks/
│   └── [2026-08] Tauri 2.0 마이그레이션/
│       ├── index.md                 # frontmatter = 업무 메타데이터 · 새 업무가 만드는 유일한 파일
│       ├── attachments/             # 파일을 가져오면 그때 생긴다 — 미리 파 두지 않는다
│       ├── 온보딩 이탈 개선.bs.md      # 브레인스토밍 — 평범한 마크다운 노트다
│       ├── reference/[참조한 업무명]/  # [참고만 하기]로 가져온 과거 업무 사본
│       ├── [2026-07] 편입된 업무/     # 다른 업무를 편입하면 폴더째로 들어온다 (아래 "업무 편입")
│       └── .context_snapshot.json   # 열린 탭 · 선택 파일 · 미저장 텍스트 · 메모
├── Templates/                       # 표준 패턴 (반복 업무)
│   ├── 릴리스 노트 양식.md            # 노트 템플릿 — 섹션 골격만
│   └── 정기 점검 패키지/              # 폴더 템플릿 — 파일 전체가 새 업무로 복사됨
├── Archive/[연도]/                  # 보관 방식이 'move'일 때만 사용
├── Wiki/                            # LLM 위키 — 완료한 업무를 AI 가 정리한 페이지 (아래 "LLM 위키")
└── _index/Archive.md                # 보관 목록 MOC (Dataview 표)
```

Vault 밖에 사는 것들:

```
%USERPROFILE%\.contextflow\
├── today.db                         # 오늘의 한일 (SQLite · 날짜별 영구 기록)
├── ai.json                          # AI 연결 설정 — 백엔드가 소유한다
├── prompts/*.md                     # 사용자 프롬프트 팩 — 사용자가 직접 넣는 폴더다
└── runs/current/                    # AI 실행의 작업 폴더 (빈 폴더로 둔다)

<app_config_dir>\settings.json       # UI 설정 — 프런트가 통째로 소유한다(업무 리스트의 묶어 보기 · 카테고리 접힘 상태도 여기 — Vault 별이 아니라 앱에 하나)
```

frontmatter 스키마:

```yaml
---
id: task-2026-0803-01
title: Tauri 2.0 마이그레이션
status: in-progress        # in-progress | on-hold | completed
tags: [dev, tauri, rust]
category: "프로젝트/Tauri"   # 카테고리 — 1~3단계, 없으면 미분류(키 자체가 없다)
created: 2026-08-03 10:00
updated: 2026-08-03 15:30
parent_task: null          # 다른 업무에 편입되면 받는 업무의 id 가 적힌다
template_ref: "[[Templates/Tauri 마이그레이션 표준절차]]"
runs: 2
order: 2048                # 업무 리스트를 끌어 옮겼을 때만 생긴다
completed_at: 2026-08-10   # 완료 시
archived: true             # 보관 시
archived_at: 2026-08-11
---
```

새 업무의 `index.md` 본문은 **`## 개요` 한 섹션뿐**이다. 체크리스트도 Run Log 도 미리
깔지 않는다 — 안 쓰는 골격은 지우는 손만 하나 더 만든다. `## 실행 이력 (Run Log)` 은
첫 회차를 기록하는 순간 생긴다(표준 패턴에서 만든 업무는 예외로, 아래 "템플릿" 참고).

frontmatter는 **줄 단위로 부분 수정**한다(`src-tauri/src/frontmatter.rs`). 상태 하나를 바꿔도
나머지 키의 순서 · 따옴표 · 본문이 바이트 단위로 보존되므로, Obsidian에서 손으로 고친 내용이
앱 때문에 재작성되지 않는다.

## 화면

| 화면 | 하는 일 |
| --- | --- |
| 워크스페이스 | 업무별 파일 트리 · 탭 에디터 · 마크다운/HTML 뷰어 · 브레인스토밍 캔버스 · 메모장. 업무 전환 시 스냅샷 저장/복원 |
| 업무 리스트 | 상태 필터(전체 · 진행중 · 보류) · 검색 · 카테고리 트리로 묶어 보기(접기 · 펼치기, 묶음 머리 `＋` 로 새 업무) · 1초 롱프레스 드래그로 순서 변경 · 아래 도크에 [오늘의 한일](건수를 누르면 날짜별 기록 팝업) |
| 템플릿 | 표준 패턴과 회차별 Run Log. "생성하지 않은 중복 노트" 수치는 실제 Vault에서 계산 |
| 보관함 | 분기별 또는 카테고리별 그룹 · 카테고리로 거르기(하위 포함, 카드의 칩을 눌러도 된다) · 본문 전문 검색 · [Obsidian] 열기 · [재개] |
| 위키 | 완료한 업무로 쌓은 LLM 위키 — 검색 · 유형별 트리 · 페이지 보기(링크 이동 · 원본 업무 열기) · AI에게 묻기(이어서 묻는 대화 · 웹 검색) · 점검 · 반영 대기와 [모두 반영] |
| 설정 | Vault 경로 · 열기 기본값 · 보관 정책 · AI 연결 3종을 탭으로(FabriX 두 방식 · Claude Code · Codex CLI) · 기능별 AI 연결과 테스트 대화 · LLM 위키 · 웹 검색 브라우저 · 프롬프트 팩 · 유사도 임계값 · 컨텍스트 보존 토글 |

보관된 업무의 상세는 **보관함 화면 안에서** 열린다. 워크스페이스로 넘기면 그쪽 업무
리스트에 없는 업무라 아무것도 고르지 않은 것처럼 보이고, 목록으로 돌아와도 이미 활성
업무라 같은 항목을 다시 열 수 없었다. 상단 바의 [← 보관함 목록]이 돌아가는 길이며,
[여기서 재개]를 누르면 그때 워크스페이스로 넘어간다.

## 업무 리스트 순서

기본은 `updated` 내림차순(최근 수정순)이다. 업무를 **1초 길게 누르면** 잡히고, 끌어서
원하는 자리에 놓을 수 있다. 탐색기 드래그와 같은 1초·같은 손동작이며, 그래서 화면마다
다른 규칙을 외울 필요가 없다. 별도의 드래그 손잡이나 정렬 모드 버튼은 두지 않는다.

순서는 각 업무 `index.md` 의 `order` 에 저장된다. Vault 를 따라 움직이고 Obsidian 에서도
보이며, 업무명을 바꿔 폴더 경로가 달라져도 값이 노트 안에 있으므로 그대로 따라온다.

* **처음 끌면 그때 보이던 순서 전체가 굳는다.** 끌어온 하나만 값을 받으면 그것만 맨 위로
  튀어 기대와 다른 결과가 된다. 이후의 드래그는 보통 노트 한 장만 다시 쓴다(값 계산은
  `vault.rs` 의 `assign_orders` 가 하고, 이미 순서에 맞는 값은 건드리지 않는다).
* **`order` 를 쓸 때 `updated` 는 갱신하지 않는다.** 순서를 바꾼 것은 업무를 *작업한* 것이
  아닌데, 목록이 바로 그 값을 "마지막 작업 시각" 으로 보여 주기 때문이다.
* 한 번도 끌지 않은 Vault 에는 `order` 키가 아예 없고, 정렬도 예전 그대로다.
* **상태 필터가 걸려 있어도 끌 수 있다.** `order` 는 상태와 무관한 하나의 줄 세우기라
  최종 순서는 살아 있는 업무 전체로 만들어야 하는데, 사용자가 자리를 고른 곳은 걸러진
  목록이다. 그래서 놓은 자리를 **새 이웃**으로 읽는다 — 보이는 목록에서 바로 뒤에 오게
  될 업무 앞(맨 끝이면 마지막으로 보이던 업무 뒤)에 끼워 넣는다. 화면에서 본 결과가
  그대로 나오면서 사이에 숨어 있던 업무들은 있던 자리에 남는다(`lib/reorder.ts`).
* **검색 중에는 끌 수 없다.** 검색 결과는 목록의 한 조각이 아니라 여기저기서 걷어 온
  것이라, 옆에 보이는 업무가 실제 이웃이라는 보장이 없다 — 놓은 자리가 곧 결과가 되지
  않으면 끌게 두지 않는 편이 낫다.
* **카테고리로 묶어 보일 때는 같은 묶음 안에서만 옮긴다.** 묶음의 업무들은 전체 순서의 한 조각이라 놓은 자리를
  위와 같은 규칙으로 읽으면 된다. 다른 묶음 위에 놓으면 **아무 일도 일어나지 않는다** — 끌어서 카테고리를 바꾸는
  것은 실수로 일어나기 쉬워 두지 않았다(카테고리는 워크스페이스 머리글의 칩으로 바꾼다). 끄는 동안 다른 묶음은
  흐려진다.
* 최근 수정순으로 돌아가려면 메뉴의 **업무 → 정렬 초기화**. 모든 노트에서 `order` 를 지운다.

## 완료하면 그 자리에서 보관한다

업무 상태를 **완료**로 바꾸면 세 가지가 한 번에 일어난다 — `completed_at` 이 적히고,
그 업무가 보관되고(`archived: true`, 보관 방식이 'move' 면 폴더가 실제로 옮겨진다),
열려 있던 그 업무의 창이 닫힌다.

예전에는 완료로 바꾼 업무가 배지만 초록으로 바뀐 채 목록 맨 위에 남았다. 끝낸 일을
목록에서 지우는 손이 한 번 더 필요했고, 보관 기준일(설정의 `archDays`)이 지나야 조용히
사라졌다 — 그 사이의 업무 리스트는 "지금 하는 일" 이 아니라 "한 일이 섞인 목록" 이다.
완료를 누른 순간이 그 업무를 손에서 놓는 순간이므로, 목록에서 빼고 창도 닫는다.

* **설정의 `자동 보관 기간` 은 이제 앱 밖에서 완료로 바뀐 업무만 다스린다.** 앱에서
  [완료] 를 누르면 `archived: true` 가 바로 적히고, `is_archived` 는 그 키를 먼저 보므로
  기간을 기다리지 않는다. 기간이 쓰이는 것은 Obsidian 에서 frontmatter 를 손으로 고친
  경우다 — `archived` 키가 없으니 그때는 `completed_at` 과 기간으로 판단한다. 설정 화면과
  보관함 머리말이 그 둘을 나눠 적는다.
* **창을 닫는 것은 다른 업무를 여는 것이 아니다.** 보관 직후 살아 있는 업무 하나를
  자동으로 골라 열면 방금 닫은 자리에 엉뚱한 업무가 나타난다. 아무 업무도 고르지 않은
  상태는 그 자체로 하나의 상태이며, 워크스페이스는 그때 "선택된 업무가 없습니다" 를
  보여 준다(업무가 아예 없을 때의 문구와 다르다).
* **열어 둔 탭 · 미저장 버퍼는 버리지 않는다.** 창을 닫기 전에 저장하고 스냅샷을 쓰며,
  메모리 캐시도 그대로 둔다. 보관함에서 그 업무를 다시 열면 있던 자리에서 이어진다.
  보관 방식이 'move' 라 폴더 경로가 바뀌면 캐시 키도 새 경로로 옮긴다.
* [지금 보관함으로] 도 같은 규칙을 쓴다 — 지금 열려 있는 업무를 보관하면 그 창이 닫힌다.
* 되돌리는 길은 그대로다: 보관함에서 [여기서 재개] 를 누르면 상태가 진행 중으로 돌아오고
  Run Log 에 재개 줄이 남는다.

### 예외 — 파일을 안 붙인 업무는 보관하지 않는다

**새 업무를 만들고 파일은 하나도 붙이지 않은 채 간단 메모장만 쓴 업무**를 완료하면, 보관
대신 오늘의 한일 한 줄로 접히고 업무 폴더는 지워진다. 그런 업무까지 보관하면 보관함이
돌아볼 값이 없는 한 줄짜리 폴더로 채워지는데, 그 업무가 남긴 것은 제목과 글뿐이고 그 둘은
기록 한 줄에 그대로 들어간다 — 폴더 하나보다 정확한 기록이다.

* **판정 기준은 둘이다.** 업무 폴더에 `index.md` 밖에 없고(점 파일은 세지 않으므로
  `.context_snapshot.json` 은 상관없다), 메모장이 비어 있지 않을 때. 메모를 조건에 넣는
  이유는 남길 글이 있어야 지우는 것이 무손실이기 때문이다 — 아무것도 쓰지 않은 빈 업무는
  예전처럼 보관한다. 파일 목록을 읽지 못했을 때도 보관으로 간다.
* **확인을 묻지 않는 대신 글을 하나도 잃지 않는다.** 기록을 **먼저** 쓰고 그 다음에
  지운다(뒤집으면 쓰기가 실패한 순간 글이 어디에도 없다). 기록의 내용에는 메모와
  `index.md` 본문이 함께 들어간다 — 새 업무 대화상자에서 적은 개요도, 나중에 직접 쓴 글도
  그 안에 있다. 앱이 만든 `## 개요` 머리말만 걷어내며, 사용자가 가운데에 또 쓴 `## 개요` 는
  건드리지 않는다.
* 이 기록의 줄은 **업무와 연결되지 않는다**(`folder` 가 비어 있다). 폴더가 사라졌으니
  눌러 갈 곳이 없고, 경로로 남기면 눌러도 아무 일이 없는 죽은 줄이 된다.
* 그날 그 업무로 이미 올라가 있던 줄은 치운다 — 같은 일을 두 줄로 세는 것이다. 지난 날짜의
  줄은 그날 실제로 손댄 기록이라 남는다.
* **삭제는 되돌릴 수 없다.** 이 앱의 삭제가 전부 그렇다(휴지통을 거치지 않는다). 안전장치는
  `vault::discard_task` 에 있다: 지울 수 있는 것은 `Tasks/` 의 직계 자식이면서 `index.md` 를
  가진 폴더뿐이다.

## 오늘의 한일

업무 리스트 아래 도크에 있는 목록이다. **업무를 고치면 그 업무의 제목이 여기에 올라온다** —
파일 저장 · 상태 변경 · 파일 만들기 · 지우기 · 옮기기 · 가져오기 · 바탕화면 반출 · 연결
프로그램으로 열기 · 업무명 변경 · 보관 · 재개 · 병합 · 편입 · 분할 · 회차 로그 · 메모장. 같은 업무는 한
줄이고 다시 건드리면 시각만 새로 적힌다.

기록은 **날짜별로 영구히** 쌓인다. 도크는 오늘만 보여 주고, 어제와 그제를 보고 고치는 곳은
머리말의 건수를 눌러 여는 팝업이다.

* **업무를 열어 본 것은 세지 않는다.** 그것까지 세면 잠깐 확인한 업무가 전부 쌓여
  "오늘 무엇을 했는지" 가 아니라 "오늘 무엇을 봤는지" 가 된다.
* **도크는 오늘만 보여 준다.** 여러 날짜로 늘리면 사이드바에서 스크롤로 과거를 뒤지게
  되는데, 그것은 이 자리가 할 일이 아니다 — 이 도크가 답하는 질문은 "오늘 무엇을 했나"
  하나다. 자정에 타이머로 화면을 새 날짜로 넘기는 것은 그대로 한다: 그것이 없으면 밤을
  넘긴 창에는 다시 그릴 일이 없어 어제 목록이 그대로 남는다. **넘어가는 것은 화면이고,
  어제의 줄은 그대로 있다.**
* **Vault 를 갈아타도 지우지 않는다.** 행마다 기록 당시의 Vault 루트를 들고 있어 남의
  Vault 의 줄이 섞여 보이지 않고, 되돌아오면 원래 기록이 그대로 있다. 열어 둔 탭 · 활성
  업무 · 파일 트리를 그때 비우는 것과는 이유가 다르다 — 저쪽은 경로가 죽지만 이쪽은
  경로째로 보관되어 있다.
* **업무명을 바꾸거나 보관하면 과거 날짜의 줄까지 따라간다.** 경로가 업무의 기본키라
  이걸 안 하면 지난주의 그 줄은 없는 업무를 가리키고, 눌러도 아무 일이 일어나지 않는다.
* **병합한 업무는 대표 노드 한 줄로 접힌다.** 접힌 쪽 폴더는 Archive 아래로 옮겨질 수 있고,
  같은 일을 여러 줄로 세는 것이기도 하다. 접히는 것은 **그날 줄 하나**이고, 지난 날짜의
  줄은 그날 실제로 손댄 기록이라 남는다.
* **완료한 업무를 돌아볼 자리가 여기다.** 완료는 그 즉시 업무 리스트에서 빠지므로
  (위 "완료하면 그 자리에서 보관한다"), 하루를 되짚는 목록은 저쪽이 아니라 이쪽이다.
  보관된 업무의 줄에는 `보관` 표가 붙고, 누르면 보관함 상세로 연다. 업무 리스트에 `완료`
  필터를 두지 않는 것도 같은 이유다 — 늘 비어 있는 칸이라 필터 셋을 넷으로 좁힐 뿐이었다.

### 팝업 — 날짜별 기록

왼쪽에 기록이 있는 날짜와 건수, 오른쪽에 그 날짜의 제목 목록이 있다. 줄을 누르면 **그 자리
에서** 제목과 내용이 열린다.

* **왼쪽이 달력 격자가 아니라 날짜 목록인 이유.** 이 화면에서 사람이 묻는 질문은 "지난
  화요일에 뭐 했지" 이고, 날짜와 건수가 한 줄에 붙은 목록이 그 답을 한눈에 준다. 월 격자는
  코드가 더 들고 빈 칸이 대부분인 화면을 그리며, 지난달로 가려면 화살표를 눌러야 한다.
  목록은 그냥 아래로 거슬러 올라가면 된다.
* **2단 안에 또 2단을 만들지 않는다.** 내용을 오른쪽 패널로 또 나누면 제목 목록이 읽을 수
  없을 만큼 좁아진다.
* **저장은 포커스가 떠날 때** 한다 — 간단 메모장이 이미 그 규칙이고, 글자마다 커맨드를 부르지
  않으면서 [저장] 버튼도 만들지 않는 방법이다. 값이 실제로 바뀌었을 때만 쓰므로 그냥 지나가며
  누른 줄은 아무것도 쓰지 않는다.
* **제거는 확인을 묻지 않는다.** 모달 위에 모달을 겹치는 것은 이 앱에서 하지 않고, 도크의
  ✕ 에도 확인이 없다 — 지우는 것은 파일이 아니라 기록 한 줄이다.
* **과거도 제한 없이 고친다.** 빠뜨린 일을 나중에 적어 넣는 것이 이 기록의 주된 쓸 일이라,
  오늘만 쓸 수 있게 하면 도크와 다를 바가 없어진다.
* **손으로 넣는 항목은 업무와 연결되지 않는다**(`메모` 표가 붙는다). 회의 · 전화처럼 앱 밖에서
  한 일도 그날의 기록이 된다. 시각은 오늘에만 적는다 — 지난 날짜에 넣는 줄의 시각은 그 일을
  한 시각이 아니라 적어 넣은 시각이므로, 적으면 틀린 값이 된다.
* 항목은 제목과 **내용**을 함께 든다. 목록에는 제목만 보이고(내용이 있는 줄에는 점이 하나
  찍힌다) 내용은 팝업에서만 다룬다.

### 저장소

`~/.contextflow/today.db`(SQLite) 한 파일이다. **Vault 밖**인 이유는 이 기록이 날짜를 축으로
한 교차 기록이라서다 — 노트로 남기면 Vault 에 날짜 노트가 하루 한 장씩 쌓이고 지우는 손이
하나 더 생기며, 업무 폴더 안에 넣으면 "9월 3일에 뭐 했지" 에 답하려고 폴더 전체를 뒤져야
한다. 날짜로 묻는 질문에는 날짜로 색인된 저장소가 답한다.

* **`folder` 에 붙은 부분 유니크 인덱스**가 스키마의 핵심이다. "같은 날 같은 업무는 한 줄"
  규칙을 DB 제약으로 지키면서, 손으로 넣는 자유 항목(`folder IS NULL`)은 몇 개든 공존한다.
* 다시 건드린 업무는 맨 위로 오고, **제목·내용만 고칠 때는 순서가 바뀌지 않는다** — 오타
  하나 고친 항목이 그날 목록의 맨 위로 튀어 오르면 안 된다.
* 하루에 몇 건까지라는 상한은 없다. 예전 `localStorage` 시절에는 60건 상한이 있었는데,
  그때는 하루짜리 목록이라 "목록이지 이력이 아니다" 가 맞았다. 이제는 이력이므로 상한이 곧
  사용자의 영구 기록을 조용히 버리는 장치가 된다.
* **저장소를 못 열어도 앱은 그대로 돈다.** 도크의 목록이 비어 보일 뿐이고, 업무를 손댈 때의
  기록 실패는 조용히 흘린다 — 파일을 저장할 때마다 경고가 뜨는 앱이 되면 그것이 더 큰
  고장이다. 반대로 사용자가 직접 연 팝업에서는 실패가 보인다. 연결은 실패해도 캐시하지
  않으므로 다음 호출이 다시 시도한다.
* `localStorage`(`contextflow.today`)에 있던 옛 목록은 첫 부팅에서 한 번 옮기고 키를 지운다.
  날짜가 과거여도 옮긴다 — 그날 그 일을 한 것은 사실이고, 이제 하루가 지났다고 버릴 이유가
  없다. **이관 완료 표시는 키의 부재 그 자체다**: 옮기기가 성공한 뒤에 지우므로 중간에
  실패하면 다음 부팅이 다시 시도하고 DB 쪽 upsert 가 중복을 접는다.

## 탐색기 드래그

파일을 1초 길게 누르면 옮기기가 시작된다. 창 안에서 놓으면 업무 폴더 안 이동이고,
커서를 창 밖으로 빼면 바탕화면 반출이다(Alt = 심볼릭 링크). HTML5 드래그를 쓰지 않는
이유는 두 가지다 — 1초 롱프레스를 native drag로 표현할 수 없고, Tauri에는 웹뷰 밖으로
파일을 넘기는 API가 없어서 창 밖 드롭은 어차피 좌표로 판정해야 한다.

창 밖에는 고스트를 그릴 수 없으므로(웹뷰 밖은 우리 화면이 아니다) **커서 자체에 배지를
붙인다** — 파란 → 이동, 초록 ＋ 복사, 보라 ↗ 링크. 버튼을 누르고 있는 동안은 OS가
포인터를 이 창에 붙잡아 두므로 바탕화면 위에서도 이 커서가 유지된다. 고스트는 창
가장자리에 붙여 어떤 파일을 쥐고 있는지 계속 보여 준다.

## 탐색기 빈 자리 우클릭 — 업무 폴더 최상위

트리의 행이 아닌 **빈 자리**를 우클릭하면 업무 폴더 최상위를 대상으로 하는 메뉴가 뜬다 —
**탐색기에서 열기**(Windows 탐색기로 업무 폴더를 연다) · 새 폴더 · 새 파일 · 새
브레인스토밍 · 경로 복사. 이름 바꾸기 · 삭제 · 바탕화면 내보내기는 업무 하나를 통째로
건드리는 일이라 이 메뉴에는 없다.

## 탐색기에서 이름 바꾸기

트리에서 **파일·폴더 우클릭 → 이름 바꾸기**. 대화상자를 띄우지 않고 **그 행 자리에서**
고친다 — 바꾸는 것이 거기 보이는 이름 하나여서, 새로 만들 때(`＋ 파일`)와 같은 모양이다.

* **이름 전체를 채워 두고 확장자를 뺀 앞부분만 고른다.** 전체를 채워야 확장자가 실수로
  날아가지 않고(이름만 적으면 `.md` 를 붙여 주는 새 파일 만들기와 달리, 이름 바꾸기는
  적은 그대로 만든다), 앞부분만 골라 두어야 바로 타이핑해 갈아 끼울 수 있다.
* **열려 있는 탭의 이름도 함께 바뀐다.** 열린 탭 · 미저장 버퍼 · 트리 펼침 · 캔버스 보기
  상태는 전부 업무 폴더 기준 상대 경로를 키로 들고 있어서, 디스크만 건드리면 그 전부가
  없는 파일을 가리킨다. 폴더 이름을 바꾸면 그 아래 경로의 접두사까지 함께 옮긴다
  (`relocateUi` — 탐색기 드래그의 이동도 같은 함수를 쓴다).
* **이름을 고쳐 쓰지 않고 거절한다.** `\ / : * ? " < > |` 이 섞였거나 점으로 시작하면
  (그런 이름은 `list_tree` 가 건너뛰어 트리에서 사라진다) 그대로 돌려보낸다. 조용히
  다른 이름으로 만들어 두면 적은 이름과 트리에 나타난 이름이 갈라지기 때문이다.
* **같은 이름이 이미 있으면 덮어쓰지 않는다.** 드래그 이동이 ` (2)` 를 붙이는 것과 달리
  여기서는 거절한다 — 이름을 직접 적는 자리라 무엇이 될지는 사용자가 정한다.
* **`index.md` 는 바꿀 수 없다.** 업무의 메타데이터 노트라 이름이 바뀌면 `scan` 이 그
  업무를 통째로 놓친다. 삭제 · 이동과 같은 이유이며, 메뉴에서 항목 자체를 빼 둔다.

## 탭 우클릭 — 닫기 세 가지

에디터 위 탭을 우클릭하면 **이 탭 닫기 · 이 탭 제외하고 전체 탭 닫기 · 전체 탭 닫기**가
나온다. 우클릭한 탭이 곧 대상이며, 활성 탭이 아니어도 그 탭을 가리킨다 — 탐색기에서
우클릭이 선택을 옮기지 않는 것과 같은 규칙이다.

* **닫는 것은 화면에서 치우는 것뿐이다.** 파일은 그대로 있고, 미저장 버퍼도 `docs` 에
  남아 있어 다시 열면 있던 글이 나온다.
* **여러 개를 닫을 때는 먼저 내려쓴다.** 탭을 닫으면 그 탭의 미저장 표시(주황 점)도 함께
  사라져, 어느 파일이 저장되지 않았는지 말해 줄 자리가 없어진다. 그래서 자동 저장이 900ms
  뒤에 할 일을 여기서 앞당긴다. 탭 하나의 ✕ 는 예전대로 그냥 닫는다 — 그 자리는 눌린 탭
  하나만 사라지고 나머지 표시는 그대로 보인다.
* **다음 활성 탭을 고르는 규칙은 넷이 같다**(`lib/tabs.ts`). 활성 탭이 살아 있으면 그
  자리를 지키고, 닫혔으면 남은 것 중 마지막이 활성이 된다. 하나도 남지 않으면 에디터는
  "열려 있는 파일이 없습니다" 로 돌아간다. 이 규칙을 순수 함수로 뽑아 둔 이유는 닫는 길이
  넷(탭의 ✕ · 메뉴 세 항목)이고, 업무 분할이 옮겨 간 파일의 탭을 걷어낼 때도 같은 함수를
  쓰기 때문이다.

## 마크다운 뷰어 · 텍스트 에디터

뷰어가 읽는 문법은 설계(`design/ContextFlow.dc.html`)의 좁은 범위에 둘을 더한 것이다 —
제목 · 구분선 · 체크리스트 · 인용 · 글머리 · 번호 목록 · **펜스 코드 블록**과, 줄 안의
`[[위키링크]]` · `` `코드` `` · `**굵게**` · `~~취소선~~`.

* **취소선**은 보통의 마크다운 뷰어(Obsidian · GitHub)가 전부 그리는 표기라, 여기서만
  물결표가 본문에 남으면 같은 노트가 Vault 안에서 두 가지로 보이기 때문에 넣었다. 그어
  지운 글은 완료된 체크 항목과 같은 회색으로 낮춘다. 물결표가 짝을 이루지 않거나
  (`~/notes` 같은 경로) 사이가 비면 취소선이 아니다.
* **코드 블록**은 업무 노트에 로그 · 명령 · 설정 조각이 들어오는 것이 예외가 아니라
  평범한 일이기 때문이다. 블록으로 읽지 않으면 그 줄들이 하나씩 문단으로 흩어지고
  ``` 세 글자가 본문에 남는다.

목록 깊이는 들여쓰기 폭이 아니라 **조상과의 상대 비교**로 정한다(`bstorm.ts` 와 같은
이유 — 편집기 설정마다 2칸 · 4칸 · 탭이 섞인다). 그래서 같은 문서가 사람마다 다른
계단으로 보이지 않는다. `#` 과 `##` 는 크기가 갈리고, 이어지는 인용 줄은 하나의
세로선으로 붙는다. 본문은 앱의 다른 곳(11.5px 위주의 조밀한 UI)보다 크고 행간이 넓다 —
목록·버튼은 훑는 것이고 노트는 읽는 것이라, 같은 크기로 맞추면 둘 중 하나가 손해를 본다.

### 코드 블록 — 다섯 줄과 [복사]

블록은 **다섯 줄까지만** 펼쳐 보이고 나머지는 카드 안에서 스크롤한다. 읽는 화면에서
이백 줄짜리 로그가 본문을 밀어내지 않게 하려는 것이다. 대신 **몇 줄인지를 머리띠에
적는다** — 잘려 보이는 화면에서 스크롤바만으로는 뒤에 두 줄이 남았는지 이백 줄이
남았는지 알 수 없다. 머리띠의 [복사]는 블록 전체를 클립보드로 옮기고, 버튼 자신이
`복사됨`으로 1.6초간 바뀐다(그래서 토스트를 띄우지 않는다 — 아래 "토스트" 참고).

여닫는 펜스는 백틱과 물결표를 모두 받으며, **닫는 쪽은 여는 쪽과 같은 글자로 같은 수
이상**이어야 한다. 닫는 펜스가 없으면 문서 끝까지가 코드다(CommonMark 와 같다) — 아직
닫지 않은 블록도 코드로 보이는 편이, 그 뒤의 모든 줄이 문단으로 흩어지는 것보다 낫다.

### 체크박스는 눌러 토글한다

뷰어에서 `☐`/`☑` 를 누르면 그 자리에서 상태가 바뀌고 파일에 곧바로 쓰인다(900ms 자동
저장을 기다리지 않는다 — 체크는 글자를 치는 것과 달리 **한 번의 완결된 동작**이다).
텍스트로 편집을 열어 대괄호 안을 고치러 갈 이유가 없어졌고, 그래서 머리띠도 이제
"읽기 전용"이라고 말하지 않는다.

고치는 것은 **그 줄의 대괄호 안쪽 한 글자뿐**이다. 줄 끝 공백 · 들여쓰기 · CRLF 개행이
그대로 남아야 Obsidian 쪽 diff 가 체크 하나에 통째로 뒤집히지 않는다. 어느 줄을 고칠지는
파서가 블록마다 들고 다니는 원본 줄 번호(`line`)로 정하고, 뷰어는 본문만 파싱하므로
본문이 시작하는 줄을 부르는 쪽이 더한다(`splitFrontmatter` 가 돌려주는 `bodyLine`).

그 값을 **프런트마터 줄 수를 세어 짐작하지 않는다.** 닫는 줄이 `---` 하나가 아닐 수
있기 때문이다 — `--- ` 처럼 공백이 붙거나 `----` 처럼 대시가 하나 더 많거나, 블록이
비어 있을 수도 있다(Obsidian 은 그 전부를 프런트마터로 읽는다). 짐작한 값이 한 줄만
밀리면 첫째 항목을 눌렀는데 둘째 항목이 토글되고, 그 사실은 화면에 드러나지 않는다.

### 이미지 — 붙여넣기와 크기 단계

클립보드에 이미지가 있을 때 `.md` 노트에 **Ctrl+V** 를 누르면, 그림이 **업무 폴더
최상위의 `images/`**(없으면 만든다)에 `image-YYYYMMDD-HHMMSS.png` 로 저장되고 그 자리에
노트 기준 상대 경로의 링크 한 줄이 들어간다 — 최상위 노트면 `![](images/image-….png)`,
`refs/` 안의 노트면 `![](../images/image-….png)`. 텍스트 에디터에서는 커서 자리에, 뷰어에서는(뷰어를 한 번 눌러 초점을 둔 뒤)
문서 끝에 붙는다. 이름에 공백 · 한글을 넣지 않는 것은 링크 경로에 그대로 들어가서다 —
인코딩 없이 Obsidian 과 이 뷰어에서 똑같이 읽혀야 한다. 같은 초에 두 장이면 `-2` 가
붙고, 이미 있는 파일은 덮어쓰지 않는다.

**클립보드에 글자가 함께 있으면 글자가 이긴다.** Excel · Word 에서 셀이나 문단을
복사하면 글자와 함께 그 모양을 찍은 그림이 같이 실리는데, 그림을 먼저 집으면 표를
붙이려던 노트에 스크린샷 파일이 생긴다. 바이트는 JSON 배열로 부풀리지 않고 IPC 본문
그대로 넘긴다(`save_pasted_image`).

뷰어는 `![alt](경로)` 와 Obsidian 의 `![[파일.png]]` 를 그린다. **이미지만 있는 줄**만
그림이 되고, 상대 경로는 업무 폴더가 아니라 **노트가 있는 폴더** 기준이다. 외부 주소는
앱 창의 CSP 가 막으므로 그리지 않고, 경로가 틀린 그림과 함께 적힌 경로를 대신 보여 준다.

그림 위에 마우스를 올리면 **작게(240px) · 중간(480px) · 크게(글줄 폭) · 원본** 단계가
뜬다. 고른 값은 Obsidian 과 같은 `![alt|240](경로)` · `![[파일.png|240]]` 표기로 문서에
곧바로 쓰인다 — 코드 블록 단계와 달리 그림 크기는 읽는 방식이 아니라 노트의 모양이라,
다시 열거나 Obsidian 에서 열어도 같아야 한다. 체크박스처럼 **그 토큰 하나만** 고친다.

텍스트 에디터에서 **아무것도 고르지 않은 채 Ctrl+X** 를 누르면 커서가 놓인 줄 하나를
통째로 잘라낸다(에디터의 관례). 줄 끝 개행까지 함께 가져가므로 빈 줄이 남지 않고,
마지막 줄에서는 딸려 나갈 개행이 없어 앞의 개행을 대신 가져온다. 구간을 골라 둔
Ctrl+X 는 평소의 잘라내기 그대로다. 실제 잘라내기는 그 줄을 선택해 두고 웹뷰에게
맡긴다 — 클립보드도 되돌리기(Ctrl+Z)도 네이티브 그대로 남는다. 웹뷰가 거절할 때만
클립보드 API 로 옮기고 본문을 직접 지운다.

## HTML 뷰어

업무 폴더에 들어온 HTML(리포트 · 대시보드 내보내기)을 앱 안에서 그대로 본다. 문서는
`asset:` 프로토콜로 **디스크에서 직접** 읽는다. `srcdoc`으로 넘기면 그 문서가 앱 창의
CSP를 물려받아(`script-src 'self'`) 안의 `<script>`가 한 줄도 돌지 않기 때문이다.
별도 출처의 평범한 문서라 옆에 있는 CSS · 이미지 · 스크립트 파일도 상대 경로 그대로
따라온다. Vault 경로는 사용자 설정값이라 `assetProtocol.scope`에 정적으로 적을 수 없고,
`init_vault`가 부팅과 Vault 변경 때마다 열어 준다.

격리는 `sandbox="allow-scripts"` 하나로 한다. **`allow-same-origin`은 절대 함께 주지
않는다** — 둘을 같이 주면 문서가 스스로 sandbox를 벗을 수 있다. 불투명 출처라 앱 창 ·
IPC · 로컬 저장소에는 닿지 못하지만, CSP를 물려받지 않으므로 외부 네트워크 요청까지
막지는 못한다. 신뢰할 수 없는 HTML이면 뷰어 머리띠의 [스크립트 끄기]로 예전의 완전
차단 모드(srcdoc + 빈 sandbox)로 되돌릴 수 있다.

## 브레인스토밍

생각을 뻗어 나가며 정리하는 캔버스다. 탐색기에서 **폴더 우클릭 → 새 브레인스토밍**으로 만들고,
파일을 열면 텍스트 대신 캔버스가 뜬다. 노드마다 상태(탐색중 · 유력 · 채택 · 보류 · 폐기) ·
상세 서술 · 근거/리스크/질문을 붙인다. 정해진 상태는 **배지 · 옅은 바탕 · 테두리** 세 가지로
한꺼번에 드러난다 — 색 하나만 바꾸면 축소한 캔버스에서 채택과 유력이 갈리지 않고, 색각 이상에서는
더 그렇다. 채택된 가지는 초록 굵은 선으로, 보류는 점선으로, 폐기한 가지는 취소선과 점선으로
남는다. 지우지 않고 남기는 쪽이 요점이다 — 왜 그 길을 접었는지가 다음에 같은 고민을
반복하지 않게 한다.

**저장 형식은 평범한 마크다운이고, 확장자는 `.bs.md` 다.** 앱 전용 포맷을 쓰지 않는 이유는
이 저장소의 원칙 그대로다 — Obsidian 에서 보이는 것이 곧 ContextFlow 에서 보이는 것이어야 한다.
`.md` 로 끝나므로 Obsidian 이 아웃라인 노트로 그냥 열고, 거기서 손으로 고친 것이 그대로 캔버스로
돌아온다. 앱은 파일 내용을 읽지 않고 경로 끝만 보고 캔버스를 고른다(`viewerFor`).

```markdown
---
type: brainstorm
title: 온보딩 이탈 개선
created: 2026-08-22 14:37
updated: 2026-08-22 15:10
tags: []
---

## 생각 트리

- 온보딩 첫 주 이탈이 42%다
    - 첫 화면에서 가장 많이 빠진다
        - ✅ 입력 필드를 3개로 줄인다
            세 개까지는 이탈이 완만하다.
            ![[attachments/funnel.png]]
            근거:: 리플레이 40건 중 31건이 3번째 필드에서 멈췄다
        - ❌ 튜토리얼 영상을 넣는다
            폐기:: 제작 비용 대비 효과가 낮다
```

* **구조는 중첩 불릿이고 노드에 id 가 없다.** 트리에서의 위치가 곧 정체성이다. 캔버스 좌표도
  저장하지 않고 열 때마다 자동 배치한다 — 손으로 고친 마크다운이 언제나 유효한 문서가 되는
  쪽이, 노드를 끌어 둔 자리를 지키는 것보다 중요하다.
* **상태는 앞머리 이모지**다: `⭐` 유력 · `✅` 채택 · `⏸` 보류 · `❌` 폐기. 탐색중에는 표시를
  붙이지 않는다 — 대부분의 노드가 탐색중이라, 붙이면 파일이 이모지로 뒤덮인다. 손으로 적어 넣은
  `🔍` 는 탐색중으로 읽되 다시 쓰지는 않는다.
* **근거 · 리스크 · 질문 · 폐기는 Dataview 인라인 필드**(`근거::`)다. 그냥 불릿인 자식 생각과
  문법으로 구분되고, Obsidian 이 렌더링해 준다. `_index/Archive.md` 가 이미 Dataview 를 쓴다.
  내용이 아직 비어 있어도 `근거::` 한 줄로 남긴다 — 지워 버리면 인스펙터에서 [＋ 근거] 로 만든
  빈 칸이 왕복 한 번에 사라져서, 버튼이 아무 일도 하지 않는 것처럼 보인다.
* **파일에는 줄 끝 공백도, 불릿 아래의 빈 줄도 남기지 않는다.** 대신 인스펙터의 입력칸이 지금
  치고 있는 글자를 그대로 들고 있다가 문서에만 다듬어 넘긴다. 돌아온 값을 그대로 다시 띄우면
  스페이스바를 누르는 순간 그 공백이 지워져 낱말을 띄어 쓸 수 없고, 상세에서 Enter 로 연 새 줄도
  사라진다. 되돌리기처럼 **밖에서** 바뀐 값은 그대로 따라간다.
* **모르는 frontmatter 키와 트리 앞뒤의 본문은 그대로 보존한다.** `frontmatter.rs` 가 `index.md`
  에 대해 그러는 것과 같은 이유다 — Obsidian 에서 손으로 고친 것이 앱 때문에 재작성되면 안 된다.
* **제목이 빈 노드는 `-` 한 글자로 적힌다.** 캔버스에서 ＋ 를 누르면 먼저 빈 생각이 생기므로,
  불릿 뒤의 공백을 필수로 두면 방금 만든 것이 다시 읽을 때 사라진다.
* 들여쓰기는 4칸으로 쓰지만, **읽을 때는 폭에 기대지 않는다.** 편집기 설정마다 2칸 · 4칸 · 탭이
  섞이므로 조상과의 상대 비교로 깊이를 정한다.

### 보기 세 가지

머리띠의 전환으로 같은 문서를 세 가지로 본다. 탭이 늘어나지는 않는다.

| 보기 | 하는 일 |
| --- | --- |
| 캔버스 | 생각을 뻗는 곳. 가지 색 · 접기 · 줌 · 팬, 채택된 경로는 굵은 초록 선 |
| 개요 | 들여쓴 읽기 화면. 캔버스에서 접어 둔 가지도 **전부** 보인다 |
| 결정 로그 | 채택 → 유력 → 보류 → 폐기로 묶어 본다. 탐색중은 아직 결정이 아니라 빠진다 |

개요와 결정 로그가 접힌 가지까지 보여 주는 것은 의도한 것이다 — 무엇을 접었는지는 캔버스의
사정이지 문서의 사정이 아니다. 결정 로그에서 항목을 누르면 캔버스로 돌아가 그 생각을 고른다.

가지 색에서 **초록은 뺐다.** 채택된 경로를 굵은 초록 선으로 잇는데 초록이 가지 색으로도 쓰이면
그 가지가 통째로 채택된 것처럼 보인다. 굵기 차이로 구분하기를 기대하는 것은 무리다.

### 그림 · 다이어그램

노드에 붙인 그림은 `![[attachments/x.png]]` 로 적힌다. Obsidian 이 그대로 임베드로 그리므로
앱에서도 Obsidian 에서도 같은 자리에 같은 그림이 보인다. 표시는 `asset:` 프로토콜로 디스크에서
직접 읽는다(`convertFileSrc`) — HTML 뷰어와 같은 길이고 CSP 도 그대로다.

붙일 수 있는 것은 **이미 업무 폴더에 있는 그림**이다. 바깥에서 가져오는 길은 탐색기 드래그가
이미 갖고 있으므로 여기서 또 만들지 않는다. 클립보드에서 바로 붙여넣는 것은 아직 없다 —
이미지 바이트를 쓰는 Rust 커맨드가 필요한데 지금은 텍스트만 쓰는 `write_text_file` 뿐이다.

### 되돌리기

`Ctrl+Z` 또는 캔버스 오른쪽 아래의 [↶ 되돌리기]. 문서 전체의 텍스트를 40단계까지 쌓아 두고
되짚는다. 파일마다 따로이며 파일을 바꾸면 비운다 — 다른 문서의 상태로 되돌아가면 안 된다.
인스펙터의 입력칸 안에서 누른 `Ctrl+Z` 는 평소의 글자 되돌리기 그대로다.

줌 · 팬 · 접힌 가지 · 고른 노드 · 지금 보는 화면은 문서가 아니라 **보기**라서 `.bs.md` 가 아니라
`.context_snapshot.json` 에 남는다. 잃어도 문서가 상하지 않는 값이고, 파일을 열어 본 사람마다 다르다.

캔버스가 고친 내용은 텍스트 에디터와 **같은 버퍼**를 지나간다. 900ms 자동 저장 · 미저장 점 ·
Ctrl+S · 업무 전환 시 저장이 그대로 적용되고, 저장 경로가 따로 생기지 않는다.

## AI 연결

연결 방법은 세 가지이고 **전부 채팅 방식**이다. 레지스트리 한 곳(`src-tauri/src/agents.rs`)이
정의하고, 셋 모두 하나의 이벤트 어휘(`RunEvent`)로 수렴한다. 레지스트리 순서가 곧 화면 순서다 —
설정의 AI 연결 탭과 모든 연결 선택기에서 FabriX 가 맨 앞이다.

| id | 이름 | 전송 | 인증 |
| --- | --- | --- | --- |
| `fabrix` | FabriX | HTTP + SSE — 아래 두 방식 중 하나 | `x-fabrix-client` · `x-openapi-token` |
| `claude` | Claude Code | 로컬 CLI (`-p --output-format stream-json`) | 없음 (CLI 자체 로그인) |
| `codex` | Codex CLI | 로컬 CLI (`codex exec --json`) | 없음 (CLI 자체 로그인) |

설정 화면은 연결마다 **탭** 하나다. 탭 머리에 상태 점이 붙고, FabriX 탭에서 고쳐 놓고 저장하지 않은
채 다른 탭으로 가면 머리에 "●" 가 남는다 — 안 보이는 탭도 그려 둬 초안이 사라지지 않는다.

**AI Pro 연결은 걷어 냈다.** 예전 `ai.json` 의 `aipro` 키는 읽을 때 버려지고, 기본 연결 · 기능별 연결이
AI Pro 를 가리키고 있었으면 그 선택도 지워진다(기본 연결은 "사용하지 않음" 으로, 기능별 연결은 "기본 연결
따름" 으로) — 선택기에 없는 값이 박힌 채 기능이 소리 없이 멈추지 않게. 임베딩 시절 설정을 AI Pro 로 옮기던
1회 마이그레이션도 함께 뺐다. FabriX 게이트웨이가 쓰던 OpenAI 호환 본문 · SSE 파서는 `openai.rs` 에 남았다.

로컬 CLI 2종은 도구를 전부 차단한 채 실행한다 — 파일을 읽거나 고치지 않고 텍스트 답변만 받으므로
권한 프롬프트가 뜰 일이 없고, 권한 우회 플래그도 쓰지 않는다. 작업 폴더는 `~/.contextflow/runs/current`
라는 **빈 폴더**여서 CLAUDE.md 자동 탐색에 Vault 가 빨려 들어가지 않는다. 위키 반영처럼 업무 내용이
필요한 일은 앱이 그 내용을 프롬프트에 실어 보낸다.

연결 설정은 `~/.contextflow/ai.json` 에 있고 **Rust 가 소유한다**(앱 설정 `settings.json` 은 프런트가
소유한다 — 파일 하나에 소유자 하나). 파싱에 실패하면 원본을 `ai.json.corrupt` 로 먼저 보존한다.
API 키와 토큰은 평문으로 저장되며, 설정 화면이 그 사실을 표시한다.

### FabriX — API 가 둘이다

FabriX 에는 같은 헤더 이름을 쓰는 **서로 다른 API 가 둘** 있다. 기준 주소 · 경로 · 모델 id 형식이
모두 달라서, 설정 카드에서 방식을 고르고 경로 조립은 `fabrix.rs` 가 한다(`apiStyle`, 비어 있으면
예전 설정 그대로 채팅 API).

| | 채팅 API (`chat`, 기본) | LLM 게이트웨이 (`openai`) |
| --- | --- | --- |
| 대화 | `POST {base}/openapi/chat/v1/messages` | `POST {base}/openapi/llm/chat/completions` (`/v1` 없음) |
| 모델 목록 | `GET {base}/openapi/chat/v1/all-models` | `GET {base}/openapi/llm/v1/models` (`/v1` 있음) |
| 모델 고르기 | 본문 `modelIds` — **UUID** | 헤더 `x-llm-model-id` — 숫자 id (본문 `model` 은 무시됨) |
| 토큰 | 받은 그대로 | `Bearer ` 접두사 필수 — 빠져 있으면 앱이 붙인다 |
| 스트림 | FabriX 자체 프레임 | OpenAI `chat.completion.chunk` + `[DONE]` (`openai.rs`) |

`{base}` 는 두 방식 모두 엔드포인트 칸에 적은 **호스트 주소**다(예: `https://fabrix.example.com`). 게이트웨이의
`/openapi/llm` 은 앱이 붙인다 — 예전처럼 그 경로까지 적어 저장한 설정은 두 번 붙이지 않으므로 그대로 동작한다.

게이트웨이 쪽은 바탕화면 FabrixSample 의 규약 그대로다. 사용자 이메일(`x-generative-ai-user-email`)은
선택 칸이고, 적으면 두 방식 모두 보낸다.

사내망에서 채팅 API 를 실제로 돌려 보고 맞춘 것들:

* **모델 id 는 UUID 다.** 직접 지정 칸에 이름("Glm 5.2")을 적으면 FabriX 가 "model_guid … valid
  UUID" 로 거절한다. 그래서 아는 목록(조회 · 캐시)에 같은 이름이 있으면 그 id 로 풀어 쓰고, 오류
  본문에는 대응 방법을 한 줄 덧붙인다.
* **추론 모델은 `THINK` 프레임으로 생각을 흘린다.** `event_status` 가 `CHUNK`(답) · `THINK`(생각) ·
  `REQUEST_ANALYSIS` · `FINAL_ANSWER`(단계 표시)이고, 생각은 답과 섞지 않고 추론으로 따로 보낸다. 생각만
  하다 상한에 닿으면 답이 비는데, 테스트 대화가 그 경우를 "추론만 하고 끝났다" 로 알린다.
* **`FR-201` 은 차단이 아니다.** `filter_block_reason` 은 통과일 때도 온다(`FR-200` passed ·
  `FR-201` allowed by the filter). `FR-2xx` 가 아니고 통과 문구도 아닐 때만 차단 사유를 오류로 띄운다.
* **추론 토큰도 출력 상한에 센다.** 그래서 위키 호출은 상한을 넉넉히 잡는다(아래 "LLM 위키").

### 기능별 연결과 테스트 대화

설정의 **기능별 AI 연결** 카드가 기능마다 쓸 연결을 정한다 — 기본 연결(= 새 업무 추천) · 위키 반영 ·
위키 질의/점검 · 웹 검색. 고르지 않은 기능은 기본 연결을 따른다(`ai.json` 의 `active` 와 `routes`). 위키
반영처럼 입력이 길고 오래 쓰는 일과 추천처럼 짧게 판단하는 일은 알맞은 모델이 달라서 나눠 둔다. **웹 검색**
은 위키 질의 중 브라우저로 가져온 웹 페이지를 읽고 필요한 사실만 추리는 모델이다(아래 "웹 검색").

* **지정한 연결을 쓸 수 없으면 그 기능은 멈춘다.** 기본 연결로 몰래 바꾸지 않는다 — 값싼 모델을
  일부러 골랐을 수 있고, 사용자가 모르는 사이에 다른 서비스로 업무 내용이 나가면 안 된다.
* 각 행의 **[테스트]** 는 그 기능이 실제로 쓸 연결로 짧은 질문을 보내 답 · 걸린 시간 · 토큰 사용량 ·
  추론 길이를 보여 준다. 모델 목록이 뜨는 것(도달성)과 모델이 답하는 것(권한 · 모델 id · 출력 형식)은
  다른 문제라서 연결 테스트만으로는 "목록은 되는데 대화는 403" 을 잡지 못한다.
* 원격 카드의 **[연결 테스트]** 는 2단계다: 모델 목록 → 실패하면 첫 모델로 최소 대화 1회. 둘 다
  실패하면 두 사유를 함께 보여 준다. 성공하면 모델 칩과 선택기가 그 자리에서 갱신된다.
* 원격 카드는 입력을 초안으로 들고 있다가 [저장] 에서 한 번에 보낸다. 저장 전에는 "저장되지 않은
  변경" 이 보이고 연결 테스트를 막는다(테스트는 저장된 설정으로 한다).
* 새 업무 추천이 AI 에서 실패하면 대화상자 하단에 **사유**가 붙는다(잘림 · 형식 위반 · 연결 실패는
  사용자가 할 수 있는 조치가 다르다). 예전에는 콘솔에만 남았다.

### 스트림 · 타임아웃

FabriX 의 두 방식은 SSE 읽기를 `sse::pump` 하나로 공유한다. 줄 단위로 자르고(WSO2 게이트웨이의 `\r\n\r\n`),
`[DONE]` 에서 멈추며, 바이트를 모았다가 줄 끝에서만 디코딩해 한글이 청크 경계에서 깨지지 않는다.

* **reqwest blocking 클라이언트는 `timeout` 을 비우면 기본 30초를 건다** — 헤더 대기와 본문 읽기
  한 번마다. 예전 코드는 "전체 타임아웃 없음" 이라고 적었지만 실제로는 30초 동안 조각이 없으면 끊겼고,
  긴 프롬프트가 첫 토큰 전에 잘려 세 번 재시도됐다. 이제 조각 사이 공백 상한을 180초(`STREAM_IDLE`)로
  **명시**한다. 전체 길이 상한은 없다.
* 읽기는 별도 스레드가 하고 펌프는 짧게 깨어나 취소 플래그를 본다 — [취소] 가 다음 줄을 기다리지 않는다.
* 호출마다 온도를 정할 수 있다(`RunArgs.temperature`, 추천 0.4 · 위키 0.2). 로컬 CLI 는 무시한다.

## LLM 위키

완료한 업무를 AI 가 읽어 **위키**로 정리한다. 카파시의 "LLM Wiki" 패턴을 이 앱에 맞춘 것이다 — 질문할
때마다 원본을 다시 뒤지는 대신(RAG), 업무를 끝낼 때마다 위키에 한 번 반영해 두고 그 위키에서 찾는다.
위키가 쌓일수록 같은 개념의 페이지가 여러 업무의 경험을 모으고, 링크가 이미 걸려 있다.

층이 셋이다.

* **원본** — 업무 폴더. 위키는 여기에 **아무것도 쓰지 않는다.**
* **위키** — `<Vault>/Wiki/` 의 마크다운. AI 가 본문을 쓰고, 앱이 경로 · frontmatter · 색인 · 기록을
  맡는다. Obsidian 에서 그대로 그래프로 보인다.
* **규약** — `Wiki/SCHEMA.md`. 처음 한 번만 앱이 씨앗을 깔고 그 뒤로는 **사용자의 파일**이다. 반영 ·
  질의 프롬프트에 "규약" 으로 실린다(앱의 응답 형식과 부딪히면 형식이 이긴다).

```
Wiki/
├── SCHEMA.md          # 위키 규약 — 사용자가 고친다
├── index.md           # 색인 — 앱이 페이지 frontmatter 로 다시 만든다(직접 고치면 덮어쓴다)
├── log.md             # 작업 기록(append-only) — "## [2026-10-02 14:05] ingest | 제목 (task-id)"
├── sources/<업무 id>.md   # 업무 1건 = 1장
├── procedures/        # 반복 작업 절차(How-to) — "그 일 어떻게 했더라" 의 답
├── topics/            # 주제 · 개념
├── entities/          # 시스템 · 서비스 · 도구(사람 페이지는 만들지 않는다)
├── answers/           # 위키에 물어 얻은 답 중 남긴 것
└── .history/<시각>/   # 덮어쓴 페이지의 이전본(최근 30회분, 점 폴더라 Obsidian 에 안 보인다)
```

### 언제 반영되나

* **[완료] 를 누르면** 보관에 성공한 뒤 뒤에서 반영된다(설정 → LLM 위키 → 자동 반영, 기본 켬). 창 닫기 ·
  목록 갱신은 반영을 기다리지 않는다. 끝나면 토스트 한 번, 진행 중에는 사이드바 도크에 "반영 중 n/m".
* **[지금 보관함으로] 처럼 완료 없이 보관한 업무는 자동 반영하지 않는다.** 위키 화면의 "반영 대기" 에
  뜨고 [모두 반영] 으로 넣는다. 이미 보관된 업무를 한꺼번에 넣는 길도 그것이다.
* 반영 연결은 기능별 연결의 **위키 반영**이다. 없으면 반영하지 않는다.
* 파일을 안 붙인 가벼운 업무(오늘의 한일로 접히는 것)는 폴더가 사라지므로 반영하지 않는다.

**반영 대기는 파일에서 계산한다.** 업무마다 소스 페이지가 있는지, 그 frontmatter 의 `source_sig`
(index.md 본문 해시 + 나머지 파일의 경로 · 크기 · 수정 시각)가 지금과 같은지를 본다. frontmatter 는
재지 않으므로 보관 자체는 변경이 아니고, 재개해서 내용을 고친 뒤 다시 완료하면 "바뀜" 으로 다시 대기에
뜬다. 큐는 파일에 남기지 않는다 — 앱을 닫아도 잃는 것이 없다(대기는 다시 계산된다).

### 반영 한 건 — 호출 두 번 이하

1. **소스 페이지 + 계획** — 업무 원본(index.md 먼저, 파일당 4,000자 · 합계 16,000자, 점 파일 ·
   심볼릭 링크 · `reference/` 사본 · 바이너리는 이름만), 로컬 검색으로 고른 관련 페이지 목록, 링크할 수
   있는 페이지 이름을 보내고 소스 페이지 본문과 맨 끝의 ` ```wikiplan ` 계획(요약 · 태그 · 함께 고칠
   페이지)을 받는다.
2. **관련 페이지**(깊이 "관련 페이지까지" 이고 계획에 페이지가 있을 때만) — 계획된 페이지들의 기존 본문을
   보내 한 번의 응답으로 고친다. 새 사실에는 `([[업무]])` 인용을, 부딪히는 내용에는 `> [!warning] 상충` 을
   남기게 한다.
3. **쓰기는 한 번에** — `wiki_apply` 가 모든 페이지를 쓰고 색인을 다시 만들고 기록을 더한다. 그 전에
   실패하거나 취소하면 **아무것도 쓰지 않는다.**

페이지마다 따로 묻지 않는 이유: 느린 연결에서 2+N 번 호출하면 업무 하나에 몇 분, 일괄 반영은 몇 시간이
걸린다. 계획 JSON 이 깨져도 소스 페이지는 쓰고, 관련 페이지가 실패해도 소스 페이지는 남는다.

**페이지는 펜스가 아니라 구분자 블록으로 받는다** — `<<<PAGE source>>>` … `<<<END>>>`. 페이지 본문은
마크다운이라 안에 ``` 코드 블록이 흔하고, 그 첫 ``` 가 바깥 펜스를 닫아 버리기 때문이다. 입력에 섞인
구분자는 무력화하고, 꺾쇠 수는 세지 않으며(사내 GLM 이 `<<<END>>` 로 닫았다), 블록 안에서 계획 펜스가
시작되면 거기서 블록을 닫는다. 닫는 줄 없이 끝난 블록은 잘린 것으로 보고 기존 페이지를 덮지 않는다.

**출력 상한은 넉넉하다** — 소스 12,288 · 관련 페이지 16,384 · 질의/점검 8,192 토큰. 추론 모델은 생각에
쓴 토큰도 상한에 세서, 사내 FabriX 에서 4,096 으로 반영해 보니 소스 페이지를 쓰던 중에 잘려 계획이 통째로
빠졌다(FabriX 는 32,768 까지 받는다). 설정의 "출력 토큰 상한" 을 적으면 그 값이 이긴다.

### 경로 · 링크 · 덮어쓰기

* **경로는 모델이 정하지 않는다.** 모델은 유형과 제목만 주고 파일 이름은 앱이 만든다(`[ ]` 제거 · 공백
  정리 · 60자 · Windows 예약어 회피). 다른 폴더에 같은 이름이 있으면 그 페이지를 고친다 — 같은 개념이
  두 장으로 갈라지지 않게. 소스 페이지는 지금 반영 중인 업무의 것만 쓸 수 있다.
* **업무 폴더로는 위키링크를 걸지 않는다.** `[YYYY-MM]` 접두사가 `[[…]]` 를 깨뜨린다. 다른 페이지는
  소스 페이지(`[[task-…|제목]]`)를 인용하고, 소스 페이지 꼬리말이 퍼센트 인코딩한 마크다운 링크로 원본
  `index.md` 를 가리킨다. 'move' 보관 · 이름 변경으로 업무가 옮겨지면 [점검] 의 [경로 고치기] 가 꼬리말과
  `task_path` 를 다시 쓴다(조회는 언제나 업무 id 로 한다).
* **모델이 본 적 없는 내용은 지우지 않는다.** 고칠 페이지는 읽은 해시를 함께 보내고, 그 사이 Obsidian
  에서 바뀌었으면 건너뛴다. 해시 없이 같은 이름의 페이지를 만들려 하면 덮어쓰지 않고 `## 추가 — 날짜`
  로 덧붙인다. 덮어쓴 것은 전부 `.history/` 에 남는다.
* **색인과 기록은 앱이 쓴다.** 둘 다 frontmatter 와 적용 결과에서 결정적으로 만들 수 있는 것이라 모델에게
  맡길 이유가 없다. 색인은 같은 페이지들이면 몇 번을 다시 만들어도 같은 바이트다(만든 시각 대신 페이지들의
  최신 `updated` 를 쓴다) — 동기화 도구가 반영할 때마다 바뀐 파일로 잡지 않는다.
* 위키 색인은 언제나 `[[Wiki/index]]` 로 링크한다 — 모든 업무에 `index.md` 가 있어 `[[index]]` 는
  엉뚱한 노트로 간다(점검이 잡는다).

### 위키 화면 — 찾기 · 묻기 · 점검

사이드바의 **위키** 도크(보관함 아래)로 들어간다. 2×2 NAV 에 다섯째 칸을 끼우면 격자가 깨진다.

* **검색** — 네트워크 없이 즉시. `recommend::tokens`(영문 단어 + 한글 바이그램) 위의 IDF 점수로 제목 ×3 ·
  요약 ×2 · 태그 ×2 · 본문(포화)을 더한다.
* **페이지** — 마크다운 뷰어로 그리고 위키링크는 이 화면 안에서 따라간다(다른 화면의 노트에서는 예전처럼
  눌리지 않는다). 업무 소스 링크는 업무 id 대신 업무 제목으로 보인다. 소스 페이지의 [원본 업무 열기] 는
  보관된 업무를 보관함 안에서, 재개된 업무는 워크스페이스에서 연다. 다른 페이지는 근거 업무를 칩으로
  보여 준다 — **위키에서 필요한 과거 업무를 찾아가는 길**이 이 둘이다.
* **AI에게 묻기** — 로컬 검색으로 고른 페이지 본문으로만 답하게 하고(근거가 없으면 "위키에 없습니다"),
  인용한 페이지와 업무로 바로 간다. 답을 받은 뒤 **이어서 물을 수 있다**(아래 "대화"). 턴마다
  [위키에 저장] 이 답을 `answers/` 로 되돌린다 — 탐색한 결과도 위키에 쌓인다.
* **점검** — 기계적 문제(깨진 링크 · 들어오는 링크 없는 페이지 · 요약 없음 · 원본 없는 소스 · 옮겨진
  업무 · 반영 뒤 바뀐 업무 · 근거보다 오래된 페이지)는 즉시, [AI 검토] 는 페이지 요약과 나가는 링크만
  보내 모순 · 빠진 페이지 · 빠진 링크를 보고받는다. **고치지는 않는다.** 바뀐 업무는 그 자리에서 [다시 반영].

### 대화 — 이어서 묻기

AI에게 묻기는 대화다. 질문 아래에 답이 쌓이고 입력칸은 맨 아래에 있다.

* **대화는 하나만, 위키 화면에 있는 동안만 이어진다.** 대화는 묻기 패널의 상태이고, 위키 화면은 탭을 옮겨도
  그 패널을 내리지 않는다 — 인용 칩으로 페이지를 읽고 돌아와도 이어서 물을 수 있고, 받는 중인 답도 그대로
  들어온다. 다른 화면(워크스페이스 · 보관함 · 설정 …)으로 가면 대화가 끝난다. 처음부터 다시 묻고 싶으면
  **[대화 초기화]**.
* **이력은 프롬프트에 접어 보낸다**(`historyBlock`). 연결이 전부 상태 없는 텍스트 스트림이라 서비스 쪽
  세션을 이어 쓰지 않는다. 앞선 턴의 질문과 답만 싣고(최근 6턴 · 답은 1,500자 · 합계 8,000자, 넘으면
  오래된 턴부터 버린다) 위키 페이지 본문은 턴마다 다시 고른다 — 앞선 프롬프트를 통째로 되풀이하면 페이지
  본문이 턴마다 쌓인다. 실패 · 취소한 턴은 이력에 넣지 않는다.
* **이어지는 질문의 페이지 고르기.** "그럼 두 번째 단계는?" 은 그것만으로는 검색이 안 된다. 그래서 지금
  질문의 검색 결과 · 앞선 답이 인용한 페이지 · 앞선 질문과 합친 검색 결과를 번갈아 골라 6장을 싣는다
  (`pickContextPages`) — 화제를 바꾼 질문이면 지금 질문의 결과가, 이어지는 질문이면 앞선 맥락이 자리를
  차지한다.
* 대화 중간의 답을 위키에 저장하면 앞선 질문도 함께 남긴다(`> 앞선 질문: … → …`). 실패한 턴의
  [다시 묻기] 는 그 질문을 입력칸에 되돌린다.

### 웹 검색 — PC 의 브라우저로

입력칸 아래의 **[웹 검색]** 을 켜 두면(설정에 남는다) 위키만으로 답할 수 없을 때 AI 가 PC 의 브라우저로
웹을 찾는다.

```
질의 모델 ──(위키로 못 답함)──▶ websearch 펜스 {"queries":[…]}
   ▲                                   │ 앱
   │                                   ▼
   │                  브라우저: 검색 결과 페이지 → 결과 앞 N장의 본문   (browser.rs, CDP)
   │                                   │
   │                                   ▼
   └──[웹1] 출처 붙은 사실 목록 ◀── 웹 검색 모델(기능별 연결 "웹 검색")이 추린다
```

* **도구 호출 대신 글로 된 약속이다.** FabriX 채팅 API 와 로컬 CLI 에는 도구 호출이 없어서, 질의 모델이 답
  대신 ` ```websearch ` 펜스로 검색어를 적게 한다(`lib/wiki/web.ts`). 펜스는 라벨이 붙은 것만 본다 — 답에
  흔한 JSON 코드 블록을 검색 요청으로 오인하면 멀쩡한 답을 버린다. 질문 하나에 **검색은 두 번까지**이고,
  마지막 바퀴는 검색 안내를 닫은 프롬프트로 답하게 한다.
* **웹 페이지는 따로 고른 모델이 먼저 줄인다.** 페이지 본문은 길고 잡음이 많아 질의 모델에 통째로 싣지
  않는다. 기능별 연결의 **웹 검색** 모델(값싸고 빠른 모델이 알맞다)이 결과 목록과 본문(페이지당 4,000자 ·
  합계 24,000자)에서 질문에 필요한 사실만 `[웹n]` 출처와 함께 추리고, 질의 모델은 그 목록과 위키로 답한다.
  웹 검색 모델에는 질문과 앞선 **질문**만 보내고 앞선 답(업무 내용)은 보내지 않는다.
* **답에는 `[웹n]` 이 붙고, 아래에 출처 칩이 뜬다**(누르면 사용자의 기본 브라우저로 연다 — AI 가 쓰는
  전용 창이 아니라). 답이 아무것도 인용하지 않았으면 정리에 쓰인 출처를 "참고한 웹" 으로 보여 준다. 검색한
  말은 답 위에 그대로 보인다. 출처 번호는 턴마다 1 부터라, 다음 턴의 이력에는 `[웹n]` 을 사이트 이름으로
  풀어 넣는다. 위키에 저장하면 `## 웹 출처` 목록이 함께 남는다.
* **실패해도 위키로 답한다.** 검색이 막히거나(보안 문자 · 네트워크) 결과가 없거나 정리 모델이 실패하면 그
  사유를 질의 모델과 화면에 함께 알린다. 정리 모델이 실패하면 결과 목록의 요약을 그대로 쓴다. 두 번째 검색이
  앞서 본 페이지만 찾으면 다시 읽지 않는다.
* **[취소] 는 그 자리에서 턴을 끝낸다.** 브라우저가 페이지를 여는 중이면 그 한 장(최대 15초)은 뒤에서 마저
  끝나지만 결과는 버린다.
* **바깥으로 나가는 것.** 검색어는 고른 검색 엔진으로 나간다 — 질의 모델에게 사내 시스템 이름 · 업무 고유
  정보 · 사람 이름을 검색어에 넣지 말라고 지시한다. 웹 글 속의 지시문은 따르지 않고 자료로만 쓰게 두 프롬프트
  모두에 적고, 구분자 · 닫는 태그는 무력화한다.

브라우저(`src-tauri/src/browser.rs`):

* **설치된 Chrome → Edge → PATH 순으로 찾는다**(설정 → 웹 검색 브라우저에서 직접 지정 가능 — 지정한 파일이
  없으면 다른 브라우저로 몰래 바꾸지 않고 실패한다). HTTP 로 검색 엔진을 직접 부르지 않고 브라우저를 띄우는
  이유는 사내망의 프록시 · 인증서 · 접근 정책이 브라우저에 맞춰져 있어서다(앱의 HTTP 클라이언트는 사내
  엔드포인트용으로 프록시를 끈다). 검색 엔진도 브라우저가 아닌 요청은 막거나 다른 페이지를 준다.
* **전용 프로필(`~/.contextflow/browser`)로 띄운다.** 평소 프로필의 계정 · 쿠키를 AI 가 조종하는 창에 내주지
  않고, Chrome 136 부터는 기본 프로필로는 원격 디버깅이 켜지지도 않는다. 포트는 `--remote-debugging-port=0` 으로
  브라우저가 고르고 프로필의 `DevToolsActivePort` 에서 읽는다(고정 포트는 다른 프로그램과 부딪힌다).
* **할 수 있는 일은 둘뿐이다** — 검색 결과 페이지에서 제목 · 주소 · 요약 읽기(`web_search`), 결과 주소 하나를
  열어 본문 읽기(`web_read`). 클릭 · 입력 · 로그인은 하지 않고, `http(s)` 가 아닌 주소(`file:` · `chrome:` ·
  `javascript:`)는 열지 않는다. 작업마다 새 탭을 열고 끝나면 닫는다. 한 번에 한 작업만 한다.
* **검색 엔진**: Google · Bing · DuckDuckGo(HTML 판) · 네이버. 엔진마다 아는 결과 모양을 먼저 보고, 셋도 못
  찾으면 제목 링크를 두루 줍는다. 되돌림 주소(DuckDuckGo `uddg` · Bing `ck/a` · Google `/url`)는 원래 주소로
  풀고, 엔진 자신의 페이지는 뺀다. 보안 문자 페이지를 알아보면 "창 보이기를 켜고 한 번 풀거나 다른 엔진을" 이라고
  알린다.
* **본문 읽기**: 메뉴 · 머리말 · 꼬리말 · 광고 · 스크립트를 숨기고(`innerText` 는 숨긴 요소를 빼고 센다) 가장
  글이 많은 본문 후보(`article` · `main` …)를 고른다. 문서가 `complete` 가 될 때까지(또는 `interactive` 에서
  3초, 전체 15초) 기다린 뒤 자바스크립트가 그릴 틈을 조금 더 준다. HTML 이 아닌 문서(PDF 등)는 읽지 않는다.
* **헤드리스가 기본**이다. 헤드리스 브라우저는 User-Agent 에 `HeadlessChrome` 을 달고 다녀 검색 엔진이
  보안 문자를 내밀기 쉬워서, 탭마다 평소 UA 와 한국어 우선 언어로 바꿔 단다. [브라우저 창 보이기] 를 켜면
  AI 가 검색하는 창이 보인다.
* **띄운 브라우저는 다시 쓰고, 10분 동안 쓰지 않거나 앱이 끝나면 닫는다**(`Browser.close`). 헤드리스면 창이
  없어 사용자가 닫을 길이 없으므로, 검색 한 번 뒤로 메모리를 붙들지 않게 한다. 다음 검색이 다시 띄운다. 앱이 닫지 못하고 끝났으면 다음 실행이
  `DevToolsActivePort` 로 남은 브라우저를 찾아 그대로 쓴다 — 같은 프로필로 또 띄우면 새 창이 기존 프로세스에
  넘겨지고 바로 끝나 버린다. 창 보이기 설정이 바뀌었으면 닫고 새로 띄운다.
* 브라우저에 인자를 더 줘야 하는 환경(`--proxy-server=…` 등)은 환경변수 `CONTEXTFLOW_BROWSER_ARGS` 로
  준다(공백으로 나눈다).

## 템플릿 · 참조 — 실제로 파일이 옮겨진다

둘 다 "새 업무를 빈 폴더에서 시작하지 않게" 하려는 장치다. 뒤집어 말하면, **파일을
미리 만드는 것은 여기뿐이다** — 템플릿 없이 만든 새 업무의 폴더에는 `index.md` 한 장만
들어 있다. 예전에는 빈 `attachments/` 도 함께 팠지만 쓰지 않는 업무에서는 영영 비어
있는 칸이 트리 맨 위를 차지했고, 그전에는 빈 `notes.md` 까지 있었다. 첨부를 가져오는
순간 `import_files` 가 그 폴더를 만들어 준다 — 필요할 때 생기는 것이 곧 있는 것이다.

(`index.md` 만은 뺄 수 없다. 업무 메타데이터가 그 frontmatter 에 있고 `scan` 이 그
파일로 업무를 찾으므로, 없으면 만들어진 업무가 목록에 아예 나타나지 않는다.)

**템플릿은 두 모양**이고 같은 id 네임스페이스를 쓴다(`template_ref` 위키링크가 하나뿐이라
같은 이름의 노트와 폴더는 함께 존재할 수 없다).

* **노트** `Templates/x.md` — 그 본문이 새 업무 `index.md` 의 골격이 된다.
* **폴더** `Templates/x/` — 폴더 안 파일이 **전부 새 업무 폴더로 복사된다**. `index.md` 만은
  복사하지 않고 그 본문을 골격으로 쓴다 — frontmatter 는 새 업무의 것이어야 하기 때문이다.
  등록은 설정이 아니라 복사다: 임의의 폴더를 고르면 `Templates/` 안으로 복사해 온다.
  경로만 참조하면 원본이 옮겨지는 순간 템플릿이 깨지고 Obsidian 에서도 보이지 않는다.

어느 쪽이든 **`## 실행 이력 (Run Log)` 섹션은 없으면 만들어 붙인다.** 장식이 아니라
`count_run_log` 와 `append_run` 이 찾는 앵커라, 템플릿이 빠뜨리면 회차 기록이 조용히 죽는다.
**템플릿에서 만든 업무만 그렇다** — 템플릿 없이 만든 업무는 개요 한 섹션으로 시작하고,
그 섹션은 첫 회차를 기록하는 순간 생긴다. 회차 수는 그때 줄 수와 frontmatter 의 `runs`
중 큰 쪽을 따르므로, 섹션이 늦게 생겨도 회차가 뒷걸음치지 않는다.

**참조**(추천 카드의 `[참고만 하기]`)는 고른 과거 업무의 파일을 새 업무의
`reference/[원본 업무명]/` 아래로 복사한다. 원본 `index.md` 도 함께 가져온다 —
개요 · 체크리스트 · Run Log 가 참조의 알맹이다. `.context_snapshot.json` 만 빼는데,
그 업무의 열린 탭과 미저장 버퍼라 남의 업무에 들어가면 안 된다.

## 카테고리 — 업무를 1~3단계로 묶는다

업무 하나에 카테고리 하나를 붙인다. `프로젝트 › ContextFlow › UI` 처럼 세 단계까지, `프로젝트 › ContextFlow`
처럼 두 단계나 `운영` 한 단계여도 된다. 여러 곳에 걸치는 꼬리표는 지금처럼 태그로 단다.

* **어디서:** 워크스페이스 머리글의 카테고리 칩(없으면 `＋ 카테고리`), 새 업무 · 업무 분할 대화상자. 보관된
  업무도 보관함 상세에서 바꿀 수 있다. 새 업무에서는 유사 업무 추천이 가리키는 카테고리를 한 번에 고를 수 있고,
  분할하면 원본의 카테고리를 물려받는다.
* **고르는 상자:** 입력하면 아는 카테고리가 걸러진다. ↑↓ 로 고르고 Enter, Tab 은 고른 경로 뒤에 `/` 를 붙여
  하위로 내려간다. 없는 경로를 치면 `＋ 새로 만들기` 가 되고, `미분류` 를 고르면 해제된다. 실제로 저장될 값을
  아래에 보여 준다.
* **저장:** `index.md` 의 `category: "프로젝트/ContextFlow"` 한 줄. 항상 큰따옴표로 쓴다 — 따옴표 없는 값은
  ` #` 뒤를 주석으로 읽기 때문이다. `/` · `\` · `›` 로 단계를 나누고, 파일 이름에 못 쓰는 글자와 `# ^ [ ] ,` 는
  `-` 로 바꾸고, 단계마다 30자에서 자른다. 4단계 이상과 `미분류/…` 는 받지 않는다. Obsidian 에서 손으로 고친
  값은 관대하게 읽는다(따옴표 없음 · 목록형은 첫 항목 · 4단계 이상은 셋째 단계에 ` · ` 로 접는다).
* **폴더는 옮기지 않는다.** 폴더 경로가 앱 전역의 기본키이고 위키 소스 페이지도 그 경로를 가리킨다. 카테고리는
  메타데이터일 뿐이다.
* **`updated` 를 바꾸지 않는다.** 순서 바꾸기와 같은 이유다 — 정리는 작업이 아니다. Run Log · 오늘의 한일에도
  남기지 않는다. 위키 소스 서명은 본문만 보므로 보관 업무에 붙여도 위키가 다시 반영 대기로 돌아가지 않는다.
* **편집 중인 `index.md` 가 되돌리지 않는다.** `index.md` 는 본문만 편집하고 저장할 때 버퍼가 가진 frontmatter 로
  다시 조립하므로, 백엔드가 frontmatter 를 고친 뒤에는 버퍼를 디스크에 맞춘다(고치던 본문은 그대로). 보류 · 재개 ·
  이름 변경 · 분할도 같은 길을 탄다.

* **묶어 보기:** 진행 중 업무에 카테고리가 하나라도 있으면 업무 리스트가 접히는 트리가 된다(`▼ 프로젝트 5` ›
  `▼ ContextFlow 3` › 업무). 묶음 안에서는 그 카테고리에 바로 붙은 업무가 먼저, 하위 카테고리가 다음이고, 형제는
  가나다(코드포인트) 순, 미분류는 맨 끝이다. 개수는 하위까지 센 것이고, 상태 필터 · 검색에 맞춰 다시 세며 빈 묶음은
  숨긴다. 검색 중에는 모두 펼친다. 접힌 상태는 `settings.json` 에 남아 재시작 뒤에도 그대로다(Vault 별이 아니라 앱에
  하나). 머리글의 `⋯` 메뉴에서 묶어 보기를 끄거나 모두 접기 · 모두 펼치기, 묶음 머리의 `＋` 는 그 카테고리를 채운
  새 업무다. 다른 곳(보관함에서 재개 · 새 업무 · 카테고리 변경)에서 연 업무는 그 묶음이 저절로 펼쳐진다 — 앱을 켤 때
  알아서 고른 첫 업무는 예외로, 접어 둔 것을 풀지 않는다.
* **보관함:** 보관 업무에 카테고리가 있으면 연도 줄 오른쪽에 `카테고리` 선택(전체 · 들여쓴 트리와 개수 · 미분류)과
  `묶기: 분기 | 카테고리` 가 생긴다. 고른 카테고리는 하위까지 거르고, 카드의 카테고리 칩을 눌러도 그 카테고리로 거른다.
* **카테고리 관리:** **업무 → 카테고리 관리…**, 업무 리스트 머리글의 `⋯`(지금 연 업무의 카테고리에서 열린다), 보관함의
  `관리…` 로 연다. 왼쪽 트리(맨 위에 미분류, 줄마다 `진행 · 보관` 개수)에서 노드를 고르면 오른쪽에 그 아래 업무가 나온다.
  - **일괄 지정:** 업무를 체크하고(Shift+클릭으로 범위) 목록 위 칸에서 카테고리를 골라 지정한다. 진행 중 · 보관 업무
    모두 된다 — 쌓인 업무를 처음 정리하는 길이다.
  - **경로 바꾸기:** 이름 바꾸기 · 다른 카테고리 아래로 옮기기 · 합치기가 모두 "앞부분 바꾸기" 하나다(`a › b › c` 를
    `a › b` 에서 `x` 로 바꾸면 `x › c`). 바뀔 업무 수와 예시를 먼저 보여 주고, 이미 있는 카테고리와 겹치면 [합치기] 로 받는다.
    대소문자만 고쳐도 된다.
  - **해제:** 상위 카테고리로 올리거나(`a › b › c` → `a › c`, 최상위면 직속 업무는 미분류로), 모두 미분류로.
  - **쓰기 전에 전부 검사한다.** 4단계가 되는 업무, 최상위로 올리면 이름이 `미분류` 가 되는 업무, 자기 하위로 옮기기가
    하나라도 있으면 아무것도 쓰지 않고 그 업무를 알린다. `updated` 는 바꾸지 않는다.
  - **파일이 잠겨 있으면(OneDrive · 백신 · 편집기) 그 업무만 남는다.** 대화상자에 남은 업무와 사유가 보이고, 닫은 뒤
    [다시 시도] 는 **남은 업무만** 다시 한다 — 이미 옮긴 업무를 두 번 옮기지 않는다. 그사이 Obsidian 에서 카테고리를 바꾼
    노트는 건드리지 않고 건너뛴다.

카테고리 목록은 따로 두지 않는다 — 업무들에 붙은 값이 곧 목록이고, 붙은 업무가 없어지면 그 카테고리도 사라진다.
Obsidian 의 카테고리별 허브 노트는 [카테고리 로드맵](docs/CATEGORY-ROADMAP.md) 의 4단계다.

## 업무명 변경

frontmatter 의 `title` 과 디스크 폴더 이름을 **함께** 바꾼다. 둘이 갈라지면 Obsidian 에서
보이는 것과 앱에서 보이는 것이 달라진다. 생성 월을 뜻하는 `[YYYY-MM]` 접두사는 유지하고,
같은 이름이 이미 있으면 업무 생성과 똑같이 `(2)` 를 붙인다. 폴더 경로가 앱 전역의
기본키라 이름이 바뀌면 열린 탭 · 미저장 버퍼가 걸린 캐시 키도 함께 옮긴다.

## 업무 편입 — 다른 업무의 하위 폴더로

**업무 → 다른 업무에 편입…** (또는 업무 제목 옆 상태 배지 메뉴). 한 업무의 폴더 전체를
받는 업무 안으로 **옮긴다**. 딸린 일이 독립된 업무로 서 있을 이유가 없어졌을 때 쓴다.

노트를 섞지 않는다. 유사 노드 병합(아래 "유사 업무 추천")과는 다른 기능이다 — 그쪽은
Run Log 를 대표 노드 하나로 접고 원본을 보관하지만, 편입은 **파일을 옮기고 아무것도
합치지 않는다**. 업무의 경계가 폴더 경계와 같다는 이 앱의 규칙을 그대로 쓰면, 편입은
`fs::rename` 한 번이다.

* **편입된 업무는 업무 리스트에서 사라지고 파일은 그대로 남는다.** `scan` 이 `Tasks/` 를
  한 단계만 보기 때문에 하위 폴더가 된 그 순간 업무가 아니게 된다. `index.md` 도 그대로
  따라가므로 개요 · 체크리스트 · Run Log 를 받는 업무의 탐색기에서 그대로 열어 볼 수 있다.
* **어디서 왔는지가 노트에 남는다.** 편입된 `index.md` 의 `parent_task` 에 받는 업무의
  id 가 적히고(스키마에 처음부터 있던 자리다), 양쪽 Run Log 에 한 줄씩 기록된다. 위키링크
  대신 id 를 쓰는 이유는 업무 폴더 이름의 `[YYYY-MM]` 접두사가 `[[...]]` 안에서 링크를
  깨뜨리기 때문이다. 업무 리스트의 자리(`order`)는 지운다 — 목록에 서지 않는 노트가 들고
  있을 값이 아니다.
* **하위 폴더 이름은 고를 수 있다.** 기본값은 원본 폴더 이름 그대로다(편입은 옮기는 일이고,
  이름까지 바꾸면 Obsidian 에서 찾던 이름이 사라진다). 받는 업무에 같은 이름이 이미 있으면
  덮어쓰지 않고 ` (2)` 를 붙인다.
* **받는 쪽 후보에서 보관된 업무는 뺀다.** 끝난 업무 안으로 살아 있는 일을 넣는 것은 업무
  리스트에서 일감 하나를 조용히 지우는 것과 같다.
* **오늘의 한일은 받는 업무로 옮긴다**(지난 날짜의 줄까지). 그 일은 이제 받는 업무의
  일부이고, 옛 경로로 남겨 두면 눌러도 아무 일이 없는 죽은 줄이 된다.
* **실패하면 아무것도 옮기지 않는다.** 가장 흔한 사유가 파일 락이다 — Windows 는 열려 있는
  파일을 쥔 채로는 그 파일을 담은 폴더도 옮기지 못한다. 그때 "옮길 수 없습니다" 로 끝내지
  않고 **어느 파일을 닫아야 하는지**까지 사유에 싣는다(`fsops::busy_files` — 쓰기로 열어
  보는 것이 그 판정이고, **실패한 뒤에만** 훑는다. 미리 훑어 막으면 읽기 전용 속성처럼
  이동과 무관한 것까지 걸려 멀쩡한 조작을 막는다. 같은 이유로 문구도 "열려 있거나 쓰기가
  막힌 파일" 이라고 짚어 볼 곳만 준다). 사유는 대화상자 안에 남으므로 — 토스트는 2.8초
  뒤 사라져 읽을 시간이 모자라다 — 그 파일을 닫고 그 자리에서 다시 누르면 된다.

## 업무 분할 — 둘로 나누기

**업무 → 업무 분할…** 고른 **최상위** 파일·폴더를 새 업무로 **옮긴다**. 한 업무 안에서
성격이 다른 일이 자라났을 때, 그 조각을 제목과 개요를 새로 붙여 독립시키는 길이다.

* **최상위만 고른다. 여러 개 고를 수 있고, 폴더는 하위 전체가 함께 간다.** 폴더 안쪽까지
  낱개로 고르게 하면 옮긴 뒤 양쪽에 반쪽짜리 폴더가 남아 어느 쪽이 원본인지 알 수 없다.
  폴더 하나를 옮기는 것이 곧 그 아래 전부를 옮기는 것이라, 이 제한은 규칙을 하나 줄인다.
* **`index.md` 는 옮길 수 없다.** 업무의 메타데이터 노트라 없어지면 `scan` 이 원본 업무를
  통째로 놓친다. 삭제 · 이름 변경 · 드래그 이동에서와 같은 금지이며, 목록에서는 "업무
  노트라 남습니다" 로 보여 준다. `.context_snapshot.json` 도 옮기지 않는다(그 업무의 열린
  탭과 미저장 버퍼다).
* **복사가 아니라 이동이다.** 끝난 뒤 같은 파일이 두 업무에 있는 일은 없다. 새 업무는
  빈 업무로 만들어지고(템플릿을 타지 않는다) 양쪽 Run Log 에 무엇이 오갔는지 남는다.
  태그는 원본에서 채워 두고 지울 수 있게 한다 — 갈라져 나온 업무도 보통 같은 결의 일이다.
* **옮겨 간 파일의 탭은 원본에서 함께 닫힌다.** 열린 탭 · 미저장 버퍼 · 트리 펼침은 전부
  업무 폴더 기준 상대 경로를 키로 들고 있어서, 디스크만 건드리면 없는 파일을 가리킨다.
  폴더는 접두사로 판정하므로 그 안의 탭이 전부 따라 닫힌다(`pruneUi` — 파일 삭제도 같은
  함수를 쓴다). 옮기기 전에 미저장 버퍼를 내려쓰는 것이 먼저다: 뒤집히면 900ms 뒤에 도는
  자동 저장이 사라진 경로에 파일을 되살린다.
* **실패하면 아무것도 옮기지 않은 상태로 돌아간다.** 항목마다 한 번씩 옮기므로 중간에
  막힐 수 있는데, 그때 이미 옮긴 것을 원본으로 되돌리고 방금 만든 빈 업무 폴더까지
  치운다 — 절반만 나뉜 업무는 어느 쪽에서도 온전하지 않다. 되돌리기까지 실패한 항목이
  있으면 그것이 **새 업무 폴더에 남아 있다는 사실**을 사유에 적는다(그 폴더는 지우지
  않는다. 그것을 지우는 것은 정리가 아니라 파일 삭제다).
* 거절될 요청으로는 업무를 만들지 않는다. 이름 검사(최상위인지 · 있는지 · 금지 대상인지)를
  전부 통과한 뒤에야 새 업무 폴더를 판다.

## 토스트

토스트는 **결과가 화면에 드러나지 않거나 되돌릴 수 없을 때만** 띄운다. 파일 트리 · 탭 ·
상태 배지가 즉시 바뀌어 보이는 일(파일 열기 · 업무 전환 · 진행 중/보류로 상태 변경 ·
저장 · 폴더 생성)은 알리지 않는다. 남는 것은 실패, 눈에 보이지 않는 부수효과(클립보드
복사 · Obsidian 대신 탐색기로 폴백), 되돌리기 어려운 조작(영구 삭제 · 병합 · 업무 편입 ·
업무 분할 · Vault 교체 · Archive 폴더로 실제 이동)뿐이다.

같은 규칙에서 갈라지는 두 경우가 있다.

* **완료는 알린다.** 목록에서 사라지고 창까지 닫히는 것은 보이지만, 그 업무가 *어디로
  갔는지*는 화면에 남지 않는다. 보관함에서 다시 열 수 있다는 말이 필요한 자리다.
* **코드 블록 [복사]는 알리지 않는다.** 눌린 버튼이 그 자리에서 `복사됨` 으로 바뀌므로
  토스트는 같은 말을 한 번 더 하는 것뿐이다. 클립보드에 **못** 올렸을 때만 띄운다.

## 유사 업무 추천

두 엔진이 같은 결과 모양 뒤에 있다.

* **local** — IDF 가중 Dice 계수 (영문 단어 + 한글 bigram 토큰), `src-tauri/src/recommend.rs`.
  네트워크 없이 항상 동작하며 기본값이자 폴백이다.
* **AI** — 설정에서 고른 연결로 후보 목록을 보내 순위와 클러스터를 받는다
  (`src/lib/recommendPrompt.ts`). 어느 단계든 실패하면 자동으로 local 로 대체하고 그 사실을
  추천 패널 하단에 표시한다.

AI 경로의 출력 계약은 "자유롭게 판단 근거를 서술한 뒤 **맨 마지막에** ` ```recommend ` 펜스 하나" 다.
네이티브 structured output 이나 도구 호출을 쓰지 않는 이유는 세 연결의 공통 분모가 텍스트 스트림
뿐이기 때문이다. 파싱은 `src/lib/fencedJson.ts` 의 공통 관문을 지나며, 가장 흔한 실패인 **출력 잘림**
(닫는 ` ``` ` 도 닫는 `}` 도 오지 않음)은 안전한 절단점을 되짚어 닫아서 앞쪽 항목을 살린다.
펜스를 못 찾으면 "서술은 반복하지 말고 펜스만 다시" 라고 **한 번만** 재질의하고, 그래도 실패하면
local 로 떨어진다. 모델이 만들어 낸 가짜 id 와 `sim` 이 없는 항목은 버린다.

Vault 가 커지면 후보 전부를 프롬프트에 실을 수 없으므로, 40건을 넘으면 local 엔진을 재현율 단계로
한 번 돌려 상위 묶음만 추린다(접힌 자식까지 펼쳐서 보낸다).

두 엔진 모두 실제 유사도를 [0,1]로 그대로 보고한다. 목업의 숫자에 맞추려고 값을 보정하지 않는다.

## 프롬프트 팩 (사용자 지침)

`~/.contextflow/prompts/*.md` 에 파일을 넣고 설정 화면에서 지점을 골라 켜면 그 내용이 그 요청에 붙는다.
프런트마터(`name` · `description` · `stage`)는 선택 사항이다(`stage` 는 권하는 지점 표시일 뿐이다). 앱은
이 폴더에 쓰지 않는다.

주입 지점은 다섯이다 — **추천 순위(`recommend.rank`) · 위키 반영(`wiki.ingest`) · 위키 질의(`wiki.query`) ·
위키 점검(`wiki.lint`) · 웹 검색 정리(`wiki.web`)**. 지점마다 켠 순서가 우선순위이고(▲/▼ 로 바꾼다) 한 지점에 5개까지다.

어느 지점이든 팩은 **출력 계약보다 앞에 놓인다.** 계약(펜스 규격)은 프롬프트
텍스트와 파서 사이의 경성 결합이라, 사용자가 그것을 덮어쓸 수 있으면 한 글자 편집이 모든 추천을
조용히 local 폴백으로 떨어뜨린다 — 그 폴백이 정당한 코드 경로라 에러조차 뜨지 않는다. 시스템
프롬프트에도 주입하지 않는다: 판단하는 쪽의 정체성이 바뀌면 점수가 왜 기울었는지 추적할 수 없다.

팩 1개는 8,000자, 훅 1개의 합성은 12,000자에서 멈춘다. 상한을 넘겨 실리지 **못한** 팩은 설정 화면이
경고로 알린다 — 조용히 빠뜨리면 켜 둔 지침이 실제로는 나가지 않는다는 사실을 알 방법이 없다.

## Obsidian 연동

`obsidian://open?path=<절대경로>` 는 **그 경로가 이미 Obsidian 에 등록된 vault 안에 있을 때만**
동작한다. 밖이면 Obsidian 이 "Vault not found" 대화상자를 띄우는데, 사용자 눈에는 ContextFlow 가
고장 난 것으로 보이고 무엇을 해야 하는지도 알 수 없다. 그래서 **쏘기 전에 먼저 확인한다.**

Obsidian 의 vault 목록은 설정 폴더의 `obsidian.json` 에 있다(Windows `%APPDATA%\obsidian\`,
macOS `~/Library/Application Support/obsidian/`, Linux `~/.config/obsidian/`). **읽기만 한다** —
남의 앱 설정 파일이고, Obsidian 이 떠 있으면 종료할 때 자기 것으로 덮어쓴다.

| 상황 | 동작 |
| --- | --- |
| 등록된 vault 안 | `obsidian://open?vault=<vault ID>&file=<상대경로>` 로 연다 |
| 등록된 vault 밖 | 죽은 URL 을 쏘지 않고 탐색기로 열며 등록 방법과 Obsidian 이 아는 vault 경로를 토스트로 알린다 |
| 목록을 못 읽음 | 아무것도 단정하지 않고 예전처럼 `path=` 로 쏜다 |
| `HKCR\obsidian` 미등록 | 탐색기로 폴더를 연다 |

`vault=`+`file=` 형식을 쓰는 이유는 **어느 vault 로 열지 우리가 지정하기 때문**이다. Obsidian 이
쓰는 vault 루트와 ContextFlow 의 Vault 경로가 달라도(예: `Tasks/` 만 vault 로 등록해 두면 업무
노트는 열리는데 루트의 `_index/Archive.md` 만 안 열린다) 충돌하지 않는다. vault 가 중첩돼 있으면
가장 깊은 것을 고른다 — Obsidian 이 실제로 그 파일을 여는 vault 가 그쪽이다.

vault 는 이름이 아니라 `obsidian.json` 의 **ID** 로 지정한다. 이름은 폴더 이름이라 서로 다른 곳의
`Notes` 두 개처럼 겹칠 수 있지만 ID 는 겹치지 않는다.

"안에 있는가" 는 적힌 경로와 **실제 위치(`canonicalize`)** 를 모두 견준다. 같은 폴더도 정션 ·
심볼릭 링크(OneDrive 의 `문서` ↔ `Documents`), 매핑 드라이브 ↔ UNC, 8.3 짧은 이름으로 다르게
불리고, Obsidian 이 기억하는 표기와 설정의 표기가 다르면 문자열 비교만으로는 등록된 vault 를
"등록 안 됨" 으로 오판한다.

URL 은 `cmd /C start` 가 아니라 `rundll32 url.dll,FileProtocolHandler` 로 넘긴다. cmd 는 URL 의
`&` 를 명령 구분자로 읽어 `&file=…` 을 잘라 버린다 — 그러면 vault 만 열리고 노트는 열리지 않는다.

"목록을 못 읽음" 을 "등록 안 됨" 과 섞지 않는 것이 중요하다. 포터블 설치이거나 Obsidian 을 아직
한 번도 실행하지 않았을 수 있고, 그 경우에도 열기는 잘 된다. 둘을 섞으면 멀쩡히 쓰던 사용자의
Obsidian 열기를 앱이 막게 된다. 설정 화면이 Vault 경로 아래에 등록 상태를 그대로 보여 준다.

Obsidian 이 제대로 떴을 때는 창이 뜨는 것 자체가 결과이므로 아무것도 띄우지 않는다.

보관 방식은 두 가지다.

* **frontmatter 태그** (기본) — 파일을 옮기지 않고 `archived: true`만 기록한다.
  위키링크 · 그래프 · 심볼릭 링크가 모두 살아 있다.
* **Archive 폴더로 이동** — `Tasks/` → `Archive/[연도]/`로 실제 이동한다.

## 알려진 제약

* **심볼릭 링크 가져오기**는 Windows에서 개발자 모드나 관리자 권한이 필요하다. 실패하면 복사로
  대체하고 어떤 항목이 대체됐는지 토스트로 알린다.
* **삭제는 휴지통을 거치지 않는 영구 삭제**다(설계 그대로). 이름을 직접 입력하는 확인이 유일한
  안전장치이며, 업무의 `index.md`는 삭제할 수 없도록 막아 두었다.
* **오늘의 한일 저장소가 깨지면 그 기능만 조용히 죽는다.** `~/.contextflow/today.db` 를
  열지 못하면 도크의 목록이 비어 보이고 업무를 손댈 때의 기록은 조용히 실패한다(앱은 그대로
  동작한다). 사용자가 직접 연 팝업에서는 사유가 보인다. 파일을 지우면 다음 실행에서 빈
  저장소로 새로 만들어지지만, 그때까지의 기록은 돌아오지 않는다 — 백업 대상이다.
* **FabriX 엔드포인트는 사내망에서만 검증 가능하다.** FabriX **채팅 API** 는 사내망에서
  테스트 대화 · 위키 반영 · 질의 · 점검을 실제로 돌려 확인했다(응답 모양은 위 "FabriX — API 가
  둘이다"). FabriX **LLM 게이트웨이** 방식은 요청 조립 · 헤더 · SSE 파싱 · 모델 목록 파싱을
  유닛 테스트로 덮었고, 실제 호출은 사내 게이트웨이 주소로 확인해야 한다.
* **웹 검색은 실제 검색 엔진으로 검증하지 못했다.** 브라우저 띄우기 · DevTools 조종 · 결과/본문 추출 ·
  재사용 · 종료는 실제 Chromium 과 로컬 페이지로 테스트했지만, 개발 환경의 네트워크가 검색 엔진을 막아
  Google · Bing · DuckDuckGo · 네이버의 **실제 결과 페이지 모양**은 확인하지 못했다. 엔진이 모양을 바꾸면
  결과를 못 읽을 수 있다 — 그때는 제목 링크를 두루 줍는 대비 경로가 돌고, 그래도 비면 다른 엔진을 고르면
  된다. PC 에서 `live_engines` 테스트(위 "실행")로 엔진별로 확인할 수 있다.
* **회사 정책이 브라우저의 원격 디버깅을 막으면 웹 검색이 안 된다**(Chrome · Edge 의
  `RemoteDebuggingAllowed` 정책). 그때는 다른 브라우저를 지정한다. 검색 엔진이 보안 문자를 내밀면
  [브라우저 창 보이기] 를 켜고 한 번 풀면 된다(전용 프로필에 쿠키가 남는다).
* **위키 반영은 업무 내용을 고른 AI 연결로 보낸다.** 텍스트 파일 본문(상한 안)이 프롬프트에 실린다.
  사외 서비스(로컬 CLI 의 클라우드 모델 등)를 반영 연결로 고르면 업무 내용이 그쪽으로 나간다 —
  기능별 연결에서 반영만 사내 연결로 지정할 수 있다. 민감 정보 마스킹은 아직 없다(로드맵).
* **카테고리 이름은 글자 그대로 비교한다(대소문자만 무시).** macOS 에서 붙여 넣은 자모 분리(NFD) 한글은
  눈에 같아 보여도 다른 카테고리가 된다 — 유니코드 정규화를 하지 않는다. 카테고리를 바꾸는 쓰기도 다른
  `index.md` 쓰기처럼 원자적이지 않아, 쓰는 도중 앱이 죽으면 그 파일이 잘릴 수 있다(로드맵 6단계 e).
  다른 업무에 편입된 노트(업무 폴더 안의 하위 폴더)는 업무 목록 밖이라, 카테고리 경로를 바꿔도 옛 값을 그대로 둔다.
  카테고리 관리의 일괄 변경 중 다른 프로그램(OneDrive · 백신 · 편집기)이 쥐고 있는 파일은 그 업무만 바뀌지 않고 남는다 —
  대화상자의 [다시 시도] 가 그 업무만 다시 한다.
* **위키 점검은 고치지 않는다.** 모순 · 빠진 페이지는 보고만 하고, 고치는 것은 사람(또는 다음 반영)이다.
* **설계의 바깥 여백을 쓰지 않는다.** 원본(`design/ContextFlow.dc.html:33`)은 앱을 10px 여백과
  회색 그러데이션 위에 띄운 카드로 그린다. 브라우저 목업에서 *데스크톱 바탕화면*을 흉내 내던
  것이라, 실제 창(`decorations: false`) 안에서는 테두리를 한 겹 더 감싼 회색 띠로만 보인다.
  그래서 앱이 창을 가장자리까지 채우고 둥근 모서리 · 그림자를 쓰지 않는다. 창 이동은
  타이틀바의 `data-tauri-drag-region`, 가장자리 리사이즈는 undecorated 창이 유지하는 OS
  리사이즈 보더가 그대로 담당한다.
* **폰트와 글자 크기가 설계와 다르다.** 설계의 IBM Plex Sans KR / IBM Plex Mono 대신 Google의
  Noto Sans KR / Roboto Mono를 쓰고, UI의 모든 글자 크기를 설계보다 1px 크게 렌더링한다(본문
  기준 10.5px → 11.5px. 마크다운 뷰어는 UI가 아니라 읽는 화면이라 더 크다 — 위 "마크다운
  뷰어" 참고). 9.5~11.5px 위주의 조밀한 화면을 읽기 편하게 하려는 것이고, 한글 음절 지원
  범위도 KS X 1001 2350자에서 11,172자 전체로 넓어진다. 대가로 번들에 들어가는 웹폰트가
  10MB → 19MB(woff2만 보면 5.3MB → 8.3MB)로 늘어난다. 무게 700은 설계와 코드 어디에서도
  쓰지 않으므로, 용량이 문제가 되면 `src/styles/global.css`의 `700.css` import를 먼저 지우면 된다.
* **`text-wrap: pretty`를 쓰지 않는다.** 커스텀 스크롤바가 레이아웃 폭을 차지하는 좁은 스크롤
  컬럼에서 Chrome 레이아웃이 무한 진동해 렌더러가 멈춘다. `src/styles/global.css`의
  `scrollbar-gutter: stable`이 근본 원인을 막고, 해당 속성은 설계에서 쓰였더라도 사용하지 않는다.
