# 업무 카테고리 로드맵

진행 중 업무와 보관함 업무를 **최대 3단계 카테고리**(예: `프로젝트 › ContextFlow › UI`)로 묶고,
Obsidian 에서 **카테고리별로 위키를 보는** 기능을 단계별 구현 계획으로 정리한 문서다. 1단계(카테고리
붙이기)부터 5단계(앱 위키 화면 · 반영 프롬프트)까지는 완료했고(#23 · #25 · #26 · #27 · #28), 6단계(있으면 좋은
것들 중 다섯 — 묻기 범위 · 창에 돌아오면 다시 읽기 · 원자적 쓰기 · 머리에 놓아 바꾸기 · 템플릿 기본 카테고리)를 이
브랜치에서 구현했다. 남은 둘(빈 카테고리 · 수동 순서 · 색, 위키 페이지의 `categories` 속성)은 하지 않기로 했다.

## 1. 요구 — 무엇을 하려는가

* 업무 하나에 카테고리 하나. 1~3단계이고 2단계짜리도 있다(예: `프로젝트 › 프로젝트명`).
* 진행 중 업무와 보관함 업무 모두에 붙이고, 그 기준으로 묶어 본다.
* Obsidian 에서 카테고리별로 위키(그 카테고리 업무에서 나온 소스 · 절차 · 주제 · 시스템 페이지)를 본다.
* 너무 복잡하지 않게. 빈 카테고리를 미리 만들거나 순서를 손으로 정하는 기능은 두지 않는다(사용자 결정).

## 2. 제약 — 설계를 정하는 것들

* **Vault 가 진실의 원천이다.** 업무 메타데이터는 `index.md` frontmatter 에만 있다. 카테고리도 거기에 둔다.
  별도 DB · 목록 파일을 두지 않는다 — 카테고리 목록은 업무들의 값에서 만들어진다(태그와 같다).
* **업무 폴더는 옮기지 않는다.** 프런트의 업무 키가 폴더 절대 경로다(활성 업무 · `uiCache` · 오늘의 한일 ·
  추천 id). `scan` 은 `Tasks/*` 와 `Archive/<연도>/*` 한 단계만 읽고, 위키 소스 페이지는 `task_path` 로
  업무 폴더를 가리킨다. 카테고리 폴더로 옮기면 이 모두가 깨진다.
* **frontmatter 는 줄 단위로만 고친다**(`frontmatter.rs`). 다른 키 · 순서 · 따옴표 · 줄바꿈은 바이트 그대로다.
  읽을 때 따옴표 없는 값의 ` #…` 를 주석으로 자르고, `quote_if_needed` 는 `#` 을 따옴표로 감싸지 않는다 —
  그래서 카테고리는 **항상 큰따옴표로** 쓴다.
* **편집기 버퍼가 frontmatter 를 되돌린다.** `index.md` 는 본문만 편집되고 저장할 때 버퍼가 들고 있던
  frontmatter 로 파일을 다시 조립한다(`EditorPane`). 이미 열린 버퍼는 다시 읽지 않는다(`openFile`).
  백엔드가 frontmatter 를 고친 뒤 버퍼를 맞추지 않으면 다음 타이핑이 카테고리를 지운다.
* **위키 페이지는 모델이 본문을, 앱이 경로 · frontmatter · 색인을 소유한다.** 위키 페이지에 카테고리를
  써 넣으면 이름을 바꿀 때마다 페이지가 흔들리고 `base_hash` 비교가 반영 중인 ingest 와 부딪힌다.
* **Obsidian 사용자는 Dataview 가 없을 수도 있다.** 카테고리별 보기는 플러그인 없이 읽혀야 한다.

## 3. 핵심 결정

| 주제 | 결정 | 이유 |
| --- | --- | --- |
| 저장 | `index.md` 의 `category: "프로젝트/ContextFlow/UI"` 한 키. 미분류면 키가 없다 | Obsidian Properties 에 Text 로 그대로 보인다 |
| 개수 | 업무당 하나(경로 1~3단계). 여러 곳에 걸치는 꼬리표는 기존 `tags` | 트리 · 개수 · 드래그가 단순하다 |
| 정리 규칙 | `/` · `\` · `›` 로 나눈다. 단계마다 `: * ? " < > \| # ^ [ ] ,` 와 제어 문자 → `-`, 공백 접기, 앞뒤 공백 · 점 제거, 30자 자르기, 빈 단계 버리기. 쓸 때 4단계 이상 · `미분류/…` 는 거절 | 파일 이름 규칙(`sanitize_name`)과 같은 선례. 허브 노트의 위키링크가 깨지지 않는다 |
| 손편집 | 읽을 때는 관대하다: 따옴표 없음 · 목록형(첫 항목) · 4단계 이상(셋째 단계에 ` · ` 로 접음) | Obsidian 에서 고친 값도 잃지 않는다. 앱이 그 업무를 다음에 쓸 때 정규형이 된다 |
| 같음 · 순서 | 비교는 소문자 경로로. 표시는 가장 많이 쓰인 철자. 형제는 코드포인트 순(한글은 가나다), 미분류는 맨 끝 | Windows 에서 대소문자만 다른 허브 파일이 생기지 않는다. Rust 와 TS 의 순서가 같다 |
| 부수효과 | 카테고리를 바꿔도 `updated` · `order` 는 그대로, Run Log · 오늘의 한일에 남기지 않는다 | 정리는 작업이 아니다(순서 바꾸기와 같은 규칙). 위키 `source_sig` 는 본문만 보므로 stale 이 되지 않는다 |
| 규칙 공유 | `src/lib/category.cases.json`(정리 규칙) · `category.tree.json`(트리 · 철자 · 순서) · `src/lib/wiki/categories.json`(위키 페이지가 드는 카테고리) 을 Rust(`include_str!`)와 TS 테스트가 함께 읽는다 | 화면이 받아 준 값을 백엔드가 거절하는 일이 없고, 허브와 화면이 같은 트리, 같은 페이지 멤버십을 쓴다 |
| Obsidian 보기 | 앱이 만드는 허브 노트 `_index/카테고리.md` · `_index/카테고리/카테고리 · 프로젝트 › ContextFlow.md` | `_index/` 는 이미 앱 몫(보관함 MOC). 접두어로 위키 페이지와 이름이 겹치지 않는다 |
| 위키 ↔ 카테고리 | 위키 페이지에는 쓰지 않는다. 소스 페이지는 `task_id`, 나머지는 `sources` 업무들의 카테고리로 그때그때 계산 | 페이지가 흔들리지 않고 ingest 와 충돌하지 않는다 |

## 4. 데이터 모델

```yaml
---
id: task-2026-1002-093000
title: 대시보드 개편
status: in-progress
tags: [UI]
category: "프로젝트/ContextFlow"
created: 2026-10-02 09:30
...
---
```

* `create_task` 는 `tags` 바로 뒤에 쓴다. 기존 노트에 처음 붙일 때도 `tags` 뒤에 끼우고, 이후엔 제자리에서
  고친다. 해제하면 키를 지운다.
* Rust `category.rs`: `normalize(값, 쓰기|읽기)` · `read(&Doc)` · `write(&mut Doc, 값)` · `set_category`.
  `TaskMeta.category: Option<String>`, `NewTask` · `SplitTask` 에 `category`.
* 커맨드 `set_task_category(root, folders, category)` → `{ tasks, changed, failed }`. 여러 업무를 한 번에
  받는다(3단계의 일괄 지정이 그대로 쓴다). 같은 값이면 파일을 다시 쓰지 않는다.
* TS `src/lib/category.ts`: `normalizeCategory` · `label`(`프로젝트 › ContextFlow`) · 카테고리 목록 · 추천.

## 5. 단계별 계획

### 1단계 — 카테고리 붙이기 (완료)

* **보이는 것:** 워크스페이스 머리글 둘째 줄 맨 앞에 칩(`프로젝트 › ContextFlow ▾`, 없으면 `＋ 카테고리`) →
  누르면 고르는 상자. 새 업무 · 업무 분할(원본 값을 미리 채움)에 카테고리 칸. 유사 업무 추천이 같은 카테고리를
  가리키면 한 번에 고르는 제안. 사이드바 행 · 보관함 카드에 흐린 라벨, 검색이 카테고리도 맞춘다.
  보관함 상세에서도 바꿀 수 있다.
* **고르는 상자(`CategoryPicker`):** 입력 + 바로 아래 펼쳐지는 목록. ↑↓ 로 고르고 Enter(한글 조합 중 Enter 는
  무시), Tab 은 고른 경로 뒤에 `/` 를 붙여 하위로 내려가기, Esc 는 닫기. `미분류 (카테고리 없음)` 과
  `＋ 새로 만들기` 줄, 실제로 저장될 값 미리보기.
* **버퍼 보호:** 백엔드가 `index.md` 를 고친 뒤 깨끗한 버퍼는 디스크 내용으로 바꾸고, 고치던 버퍼는 본문을
  그대로 둔 채 frontmatter 만 디스크 것으로 맞춘다. 같은 문제가 있던 보류 · 재개 · 이름 변경 · 분할(원본)과
  스냅샷에서 되살린 버퍼에도 적용한다.
* **완료 조건:** 지정 직후 `index.md` 를 타이핑해도 카테고리가 남는다. 재시작해도 남는다. Obsidian 에서
  `updated` 가 그대로다. 보관 업무의 위키 상태가 fresh 로 남는다.

### 2단계 — 카테고리로 묶어 보기 (업무 리스트 트리 · 보관함 필터, 완료)

* **보이는 것:** 진행 중 업무에 카테고리가 하나라도 있으면 업무 리스트가 접히는 트리가 된다
  (`▼ 프로젝트 5 › ▼ ContextFlow 3 › ● 업무`). 미분류는 맨 끝. 접힌 상태는 재시작 뒤에도 남는다. 상태
  필터 · 검색은 개수를 다시 세고 빈 묶음을 숨기며, 검색 중에는 모두 펼친다. 머리글 메뉴에 묶어 보기 끄기 ·
  모두 접기 · 모두 펼치기. 묶음 머리 `＋` 로 그 카테고리의 새 업무.
* **보관함:** `카테고리` 선택(전체 · 들여쓴 트리와 개수 · 미분류)으로 하위까지 거른다. `묶기: 분기 | 카테고리`.
  카드의 카테고리 칩을 누르면 그 카테고리로 거른다.
* **드래그:** 같은 묶음 안에서만 순서를 바꾼다. 묶음의 행은 전체 순서의 부분열이라 `reorderedList` 를 그대로
  쓴다. 묶음 밖에 놓으면 취소한다. 다른 묶음으로 끌어 카테고리를 바꾸는 것은 실수하기 쉬워 6단계로 미뤘다 — 6단계
  (a) 에서 다른 묶음 **머리**에 0.3초 머물렀다 놓는 것으로 더했다.
* **자동 펼침:** 사용자가 연 업무(재개 · 새 업무 · 카테고리 변경 포함)의 묶음은 저절로 펼친다. 앱을 켤 때 알아서
  고른 첫 업무는 펼치지 않는다 — 그래야 접어 둔 상태가 재시작 뒤에도 남는다. 접힘 상태는 `settings.json` 에 앱 전체
  하나로 둔다.
* **구현:** 순수 함수 `flattenSideRows`(순서 · 철자는 `knownCategories(진행 중)`, 개수 · 행은 보이는 업무) ·
  `groupArchived` · `isWithin` · `openFor` 에 규칙을 두고 테스트한다. `Sidebar.tsx` 는 행을 `TaskRow` 로 뽑고
  `CategoryRow` 를 더하되, 카테고리가 없을 때의 평면 목록 경로는 그대로 둔다. 백엔드 변경 없음.

### 3단계 — 카테고리 관리 (일괄 지정 · 경로 바꾸기 · 해제, #26)

* **보이는 것:** `카테고리 관리` 대화상자. 왼쪽 트리(맨 위에 미분류 고정 — 정리를 시작하는 곳, 줄마다 진행 · 보관
  개수), 오른쪽 그 노드의 업무 목록(체크 · Shift 범위 선택 · 검색 · `진행 중만 | 보관 포함`)과 목록 **위** 의
  [카테고리 지정] 줄(고르는 상자의 목록이 아래로 펼쳐지므로 맨 아래에 두면 입력 칸이 튄다). 쌓인 업무를 몇 번에
  정리할 수 있다. 여는 길은 **업무 → 카테고리 관리…**, 업무 리스트 `⋯`(지금 연 업무의 카테고리에서), 보관함
  `관리…`. 묶음 머리 우클릭은 4단계에서 묶음 머리 메뉴('Obsidian에서 보기' 와 함께)로 더했다.
* **노드 동작:** [경로 바꾸기] — 이름 바꾸기 · 상위 옮기기 · 합치기가 모두 "앞부분 바꾸기" 하나다. 바뀔 업무
  수를 미리 보이고, 대상이 이미 있으면 [합치기] 확인을 받는다. [해제] — 상위로 올리거나 미분류로.
* **구현:** 커맨드 `move_category(root, from, to, allow_merge, only)` · `clear_category(root, from, only)`. 쓰기 전에
  전부 검사한다(4단계 넘침 · 최상위로 올리면 `미분류` 가 되는 이름 · 자기 하위로 옮기기 거절). 업무마다 옛 값과 새 값을
  먼저 정하고(계획), 쓸 때 파일의 지금 값이 옛 값이 아니면 건드리지 않는다 — 그사이 Obsidian 에서 바뀐 노트는 건너뛴다.
  잠긴 파일은 실패 목록으로 알리고 [다시 시도] 는 **실패한 업무만** 다시 한다(같은 이동을 통째로 다시 하면, 상위로
  올리는 이동에서 `a/b/b` 처럼 이미 옮긴 업무가 다시 옮겨질 수 있다). 합치기 판정에서 목적지로 가는 길(상위로 올릴 때의
  부모)은 겹쳐도 합치기가 아니다.

### 4단계 — Obsidian 에서 카테고리별로 보기 (허브 노트 · 보관함 MOC 고침, #27)

* **허브 노트(플러그인 없이 읽힌다, `hub.rs`):**
  * `_index/카테고리.md` — 전체 트리(탭 들여쓰기), 줄마다 하위 허브 링크와 `업무 12 (진행 3 · 보관 9) · 위키 9`.
    미분류 줄은 맨 끝에서 정리할 목록을 겸한다("카테고리 관리… 에서 정리합니다").
  * `_index/카테고리/카테고리 · 프로젝트 › ContextFlow.md` — 노드마다 하나(중간 노드 포함). 빵부스러기, 하위
    카테고리, 진행 중 업무(` · 보류` · ` · 완료` 꼬리), 보관 업무(위키 소스 페이지로 링크, 아직 없으면 업무 노트로
    링크 + "위키 반영 전"), 그 업무들에서 나온 위키 페이지(절차 · 주제 · 시스템 · 질의 답변 순). 하위 카테고리까지
    합쳐 보이고, 하위 업무에는 상대 경로 라벨(` · UI › Mobile`)을 붙인다. 빈 절은 쓰지 않는다.
  * `카테고리 · 미분류.md` — 미분류 업무가 있을 때만. `Wiki/index.md` 의 허브로 가는 한 줄은 앱이 만든(표식 있는)
    전체 허브가 있을 때만 넣는다 — 허브가 없는 Vault 에 죽은 링크를 만들지 않는다. 허브를 쓸 때 색인을 다시 만드는
    것은 그 색인이 앱이 만든 것(`type: index`)일 때뿐이고(같은 이름의 사용자 노트를 덮어쓰지 않는다), 색인을 쓰지
    못해도 허브 쓰기 · 직접 열기는 성공으로 둔다(편의 줄이다).
* **규칙:** 바이트가 고정된다(시각 · `updated` · `order` · 회차를 넣지 않고, 트리는 `BTreeMap` 으로, 바뀐 경우에만
  쓴다). **허브 · 위키 링크는 Vault 루트부터의 전체 경로 위키링크다**(`[[_index/카테고리/…|이름]]` — `Wiki/index.md` 의
  `[[Wiki/SCHEMA|…]]` 선례). `카테고리.md` 같은 흔한 이름이 사용자 노트와 겹쳐도 맞게 간다. 업무 링크는 `[YYYY-MM]`
  괄호 때문에 위키링크 대신 인코딩한 마크다운 링크(위키 소스 페이지 꼬리말과 같은 방식). 앱이 만든 표식
  (`type: category-hub`, `generator: contextflow`)이 있는 파일만 고치거나 지우고, 같은 자리에 사용자 파일이 있거나
  읽지 못하면 덮어쓰지 않고 `conflicts` 로 알린다(자동 갱신은 토스트 한 번, 직접 열려던 허브면 실패). 허브 하나를
  쓰다 실패해도(동기화 도구가 잡고 있는 등) 나머지 허브와 색인은 쓰고, 직접 열려던 허브가 그것일 때만 실패로 돌려준다.
  옛 허브는 쓰기 전에 먼저 지운다 — 대소문자만 바뀐 철자에서 OS 가 어느 이름을 남기는지에 기대지 않는다. 노드 허브
  이름(확장자 빼고)은 240바이트(`MAX_STEM`)에서 막는다 — ext4 · APFS 는 이름 하나가 255바이트라 한글 30자 × 3단계면
  넘는다. 넘을 때만 글자 경계에서 자르고 경로의 FNV-1a 해시(`… 1a2b3c4d`)를 붙여, 앞부분이 같은 형제와 겹치지 않고
  바이트도 고정된다. 파일 이름 · 위키링크 · 정리 · 직접 열기가 모두 같은 이름(`hub_stem`)을 쓴다. Dataview 표는
  ContextFlow 폴더가 곧 Obsidian vault(루트에 `.obsidian/`)일 때만 접어서 덧붙이고, 목록형 `category` 는
  `category::read` 처럼 첫 항목으로 본다(목록째 `startswith` 에 넘기면 모든 노드에서 참이 된다).
* **카테고리를 쓴 적 없는 Vault 에는 만들지 않는다:** 자동 갱신은 카테고리가 하나라도 있거나 앱이 만든 허브(전체
  허브나 `_index/카테고리/` 의 표식 있는 노트)가 이미 있을 때만 쓴다(§8-4 — 그 전에는 미분류만 보인다). 직접 열기는
  그때도 쓰고, 그 뒤로는 자동 갱신이 허브를 지킨다 — 전체 허브를 지웠거나 그 자리가 사용자 노트여도 남은 노드 ·
  미분류 허브는 계속 정리하고 고친다. 전체 허브는 어느 쪽도 지우지 않아 `Wiki/index.md` 의 허브 줄이 켜졌다 꺼졌다
  하지 않는다.
* **갱신 시점 — `syncMoc` 대신 서명 구독(`src/store/indexSync.ts`):** 보관함 MOC 를 부르던 `syncMoc` 과 여섯 호출
  지점을 걷어 냈다(새 업무 · 분할 · 기록 후 삭제 · 카테고리 변경은 빠져 있었다). 스토어를 구독해 몇 값만 견주고,
  0.8초 조용하면 노트에 실리는 값의 서명을 만들어 바뀐 쪽만 쓴다. 서명은 둘이다 — MOC 는 보관 업무만(진행 중 업무를
  고쳐도 Vault 전체 scan 이 돌지 않는다), 허브는 업무 전체(폴더 · id · 제목 · 상태 · 보관 · 완료일 · 카테고리 · 생성일)와
  위키 페이지(경로 · 유형 · 제목 · 요약 · `sources` · `task_id`). `updated` · `order` 는 넣지 않는다. 앱을 켤 때 한 번
  쓰고, 한 번에 한 쓰기만 돌며(그사이 바뀌면 끝난 뒤 한 번 더), 실패하면 혼자 다시 시도하지 않고 다음 변화 때 쓴다.
  **위키 반영이 도는 동안은 허브만 미루고 끝나면 한 번 쓴다. MOC 는 바로 쓴다** — [완료] 는 곧바로 반영 큐를 돌리므로,
  기다리면 방금 보관한 업무가 큐가 끝날 때까지 MOC 에 없다. 설정 `카테고리 허브 노트 자동 갱신`(`catHubs`, 기본 켬)으로 끈다.
  끄면 남은 노트는 그대로 둔다. 사용자가 그 노트를 지워도 `Wiki/index.md` 의 허브 줄은 다음 위키 쓰기(`wiki::apply`)
  때까지 남는다 — 끄는 순간에는 허브가 아직 있어 색인을 다시 만들어도 줄이 남으므로, README 에 그 사이 누르지
  말라고 적었다.
* **색인 잠금:** `_index/*` 쓰기(허브 · MOC)는 `INDEX_LOCK` 하나로 줄 세운다. `Wiki/index.md` 다시 만들기는 페이지를
  읽을 때부터 쓸 때까지 따로 잠근다 — 임시 파일 이름(`index.md.tmp`)이 늘 같아, 반영과 허브 갱신 · 직접 열기가 겹치면
  한쪽 rename 이 실패해 페이지는 썼는데 반영이 실패로 보였다. 잠금 순서는 허브 = `INDEX_LOCK` → 색인, 반영 = 색인만이라
  교착이 없다. 세 커맨드(`write_category_hubs` · `category_hub_path` · `write_archive_moc`)는 블로킹 풀에서 돈다.
* **보관함 MOC 고침(`_index/Archive.md`):** Dataview 는 `FROM "Tasks" OR "Archive"` 로 옮겨 보관한 업무까지 보고,
  폴더 깊이 regex 로 `reference/` 사본 · 편입된 노트를 빼며, 나이로 보관하는 규칙(`completed_at AND …`)까지
  `is_archived` 와 같다. 정적 표는 인코딩한 링크 · 카테고리 열(`a › b`) · 칸의 `|` 이스케이프 · 완료일 순이고
  "최종 갱신" 시각은 뺐다. 보관 업무가 없고 파일도 없으면 자동 갱신은 만들지 않는다(시작할 때 쓰므로 보관한 적 없는
  Vault 에 빈 MOC 가 생기지 않게). 보관함의 [Archive MOC 노트 열기] 는 `force` 로 빈 목록으로라도 만든다 — 열 노트가
  있어야 한다. 보관함 오른쪽 패널의 쿼리 미리보기도 같은 글자다(`archiveDataview`).
* **앱에서 열기:** 업무 리스트 묶음 머리 우클릭 메뉴(`Obsidian에서 보기` · `이 카테고리로 새 업무` · `카테고리 관리…`,
  `CategoryMenu`), 전체 허브는 **업무 → 카테고리 허브 열기** 와 머리글 `⋯` 의 `카테고리 허브 열기`(`⋯` 는 진행 중 업무에
  카테고리가 있을 때만 보여, 보관 업무만 분류한 Vault 를 위해 메뉴 띠에도 둔다), 관리 대화상자 노드의
  `Obsidian에서 보기 ↗`, 보관함 카테고리 묶음 머리의 [Obsidian]. 프런트는 키(`keyOf`)만 넘기고 파일 이름은 백엔드가
  전체 업무로 정한다 — 화면마다 표시 철자를 정하는 범위가 다르다(사이드바 = 진행, 보관함 = 보관, 허브 = 전체). 열 때는
  설정과 상관없이 허브를 모두 다시 쓴다. macOS · Linux 는 탐색기 열기로 대신하고, `Tasks/` 만 vault 로 등록했다면 `_index/` 는 열 수
  없다(README 에 적었다).

### 5단계 — 앱 위키 화면에서도 카테고리별로 · 반영 프롬프트에 카테고리 (#28)

* **보이는 것:** 위키 화면 왼쪽 제목 줄 아래에 `카테고리` 선택(전체 · 페이지가 있는 노드만 들여쓴 트리 · 미분류, 괄호는
  하위까지 센 페이지 수). 고르면 하위까지 거르고 유형별 목록 · 머리의 개수 · 검색 결과 · 첫 화면(절차 · 최근 갱신)이
  따른다. 검색은 거르는 동안 결과를 모두 받아 거른 뒤 30건으로 자른다(먼저 자르면 다른 결과에 밀려 사라진다).
  Obsidian 버튼은 그 허브를 연다. 페이지 패널 머리에 카테고리 칩(둘까지 + `외 n`) — 누르면 그 카테고리로 거르고 열린
  페이지는 그대로다. 카테고리를 쓰지 않는 Vault 에서는 지금 화면 그대로이고, 반영 대기 · 묻기 · 점검은
  거르지 않는다(묻기 한정은 6단계 c).
* **프런트에서 계산한다(계획을 바꿨다):** 원래는 `wiki::status` 가 페이지마다 카테고리를 실어 주려 했다. 그런데 위키
  상태는 업무 카테고리를 바꿔도 다시 읽지 않아(부팅 · 위키 화면 진입 · 반영 · 묻기 저장 · 점검의 경로 고치기 때 읽는다)
  필터와 칩이 낡는다. 프런트에는
  전체 업무(`vault::scan`, 허브와 같은 목록)와 페이지의 `taskId` · `sources` 가 이미 있으므로 순수 모듈
  `src/lib/wiki/categories.ts` 가 그때그때 센다 — 늘 최신이고 백엔드 코드는 바뀌지 않았다(대조 테스트만 더했다). 거르기
  값은 `archCat` 처럼 스토어(`wikiCat`)에만 두고, 카테고리 관리의 경로 바꾸기 · 해제(`followMove`)가 새 키로 옮기며,
  고른 카테고리에 페이지가 없어지면 전체로 돌린다.
* **규칙은 허브(`View::members` · `wiki_of` · `sources`)와 같다:** 소스 페이지는 `taskId` 업무, 나머지는 `sources`
  업무들의 카테고리에 든다. 같은 id 의 업무가 여럿이면 모두이고, 보관 여부는 보지 않는다. 어느 업무와도 이어지지 않은
  페이지(출처 없는 답변 · 지워진 업무만 가리키는 페이지 · 고아 소스)는 미분류에도 들지 않는다. 상위 노드의 개수는 하위의
  합이 아니라 합집합이다. 공용 fixture `src/lib/wiki/categories.json` 을 TS(`categories.test.ts`)와 Rust(`hub.rs` 의
  `wiki_membership_matches_the_shared_fixture`)가 함께 읽고, 기대 키 집합이 노드 키(+ 미분류)와 같음도 assert 해
  "어디에도 없음" 까지 맞춘다.
* **허브와 다른 곳(보이는 방식만):** 어느 페이지가 어느 카테고리에 드는지는 같다. (1) 허브의 '위키' 절 · `위키 N` 은
  소스가 아닌 페이지만 센다 — 화면의 개수는 소스 페이지를 포함해 그만큼 크다. (2) 허브는 소스 페이지를 보관 업무의
  '보관' 절에서만 링크한다 — 화면은 진행 중 업무(반영 뒤 [재개])의 소스 페이지도 넣는다. (3) 같은 `taskId` 의 소스
  페이지가 둘 이상이면 허브는 경로순 마지막 하나만 쓴다 — 화면은 모두 넣는다.
* **반영 프롬프트:** 업무 정보의 제목 다음 줄에 `- 카테고리: 프로젝트 › ContextFlow`, 출력 형식 1번(소스 페이지)
  안내에 "분류는 관련 페이지를 고르는 데만 참고하고 소스 페이지 본문 · wikiplan `tags` 에 옮겨 적지 않는다" 한 줄.
  미분류면 둘 다 없다(`label(null)` 이 `미분류` 라 분류 이름처럼 읽힌다). 관련 페이지 검색어에는 카테고리의 단계
  이름들을 더한다. 태그에서 카테고리 낱말을 지우는 후처리는 하지 않고(마지막 단계는 정당한 태그일 수 있다), 관련
  페이지 고치기 프롬프트(`buildIntegratePrompt`)에는 넣지 않는다.

### 6단계 — 있으면 좋은 것들 (이 브랜치)

* 후보는 일곱이었다 — (a) 다른 묶음으로 끌어 놓아 카테고리 바꾸기 · (b) 템플릿의 기본 카테고리 · (c) `AI에게 묻기` 를
  한 카테고리 안으로 · (d) 창에 돌아올 때 다시 읽기 · (e) `index.md` 원자적 쓰기 · (f) 빈 카테고리 · 수동 순서 · 색 ·
  (g) 위키 페이지의 `categories` 속성. (a)–(e) 를 했고 (f) · (g) 는 처음 결정과 맞지 않아 하지 않는다(아래).
* 데이터 모델은 그대로다 — 새 값은 템플릿 frontmatter 의 `category`(업무와 같은 형식) 하나뿐이고, 목록 파일도 위키
  페이지 속성도 없다. 폴더는 옮기지 않고 `updated` · `order` 는 그대로, 버퍼 보호(`resyncIndexDocs` · `writingMeta`)를 지킨다.
* **(c) AI에게 묻기를 한 카테고리 안으로.** 묻기 단추 줄의 `범위` 선택(위키 화면의 거르기와 같은 목록).
  * 스토어 `askCat: { key } | null` — `null` 이면 화면 거르기(`effCat`)를 따르다가 **질문하는 순간 고정한다.** 대화 중에
    페이지 칩을 눌러도 범위가 몰래 바뀌지 않게. [대화 초기화] · 위키 화면을 떠날 때(언마운트) 풀고, `followMove` 가 고정한
    키도 옮긴다(모두 미분류면 `""`, 최상위에서 올려 키가 비면 고정된 전체). 유효 범위는 렌더에서 순수 함수
    `askScope(sel, counts)` 로 센다 — 페이지가 있을 때만 범위, 아니면 전체(`effCat` 과 같은 규칙). effect 가 없어 루프가 없다.
  * `askWiki({ scope })`: 멤버십은 5단계 규칙(`taskCategories` · `inCategory`)으로 **물을 때 새로 읽은 페이지로** 다시
    센다 — 0건이면 묻지 않고 오류. 두 검색은 페이지 수만큼 받아 범위로 거른 뒤 6장으로 자르고(`narrowHits` — 먼저 자르면
    범위 밖 결과에 밀린다, 5단계 검색과 같은 이유), 앞선 인용(`carry`)은 거른 뒤 셋, 프롬프트의 페이지 목록도 범위만.
  * **거르지 않는 것:** 인용 풀이는 전체 페이지로(답이 범위 밖을 링크해도 칩으로 열린다), 이력, 웹 검색. [위키에 저장] 은
    그대로다 — 인용한 페이지의 `sources` 로 그 카테고리에 저절로 든다.
  * 프롬프트는 범위가 있을 때만 네 문구(질문 머리 · 목록 머리 · 근거가 없을 때 웹 끔/켬)가 바뀐다. 범위가 없으면 한 글자도
    바뀌지 않는다(테스트). 질문 머리에 `‘a › b’ 안에서` 를 남긴다.
* **(d) 창에 돌아오면 다시 읽기.** Obsidian 에서 손으로 고친 값이 다음 계기를 기다리지 않고 보인다.
  * 신호는 Tauri `onFocusChanged`(OS 창 포커스) — DOM focus · visibility 는 HTML 뷰어 iframe 에서도 흐려지고 Alt-Tab
    사이에도 보인다. 흐려지면 `saveAll`. 돌아오면 `shouldReload`(1초 넘게 떠나 있었고 지난 다시 읽기에서 3초)일 때
    0.25초 뒤 `refreshFromDisk`, 그 사이 다시 흐려지면 취소. 1초는 앱이 Obsidian 을 띄우는 깜빡임을 거른다.
  * **앱이 쓰는 중이면 건너뛴다**(`metaWrite` · 저장 · 카테고리 관리 · 편입 · 분할 · 새 업무) — 간격에 세지 않는다. 읽는
    사이에 쓰기가 끼면(`tasks` 동일성 · `metaGen` · `saving`) 그 회차를 통째로 버린다. 같은 목록(JSON)이면 넣지 않는다.
  * 버퍼는 **저장하면 앱이 이긴다**: 고치던 노트는 그대로, `index.md` 는 frontmatter 만 디스크를 따르고(`resyncIndexDocs`),
    깨끗한 노트는 읽기 전과 같은 버퍼 객체일 때만 바꾼다. 탭 없는 깨끗한 버퍼와 다른 업무 캐시의 깨끗한 버퍼는 버린다.
  * 열린 업무의 폴더가 사라졌으면 같은 id 의 업무가 딱 하나일 때 따라가고(`renameTask` 에서 뽑은 `followFolder`), 아니면
    저장 없이 닫는다 — 다음 자동 저장이 옛 자리에 폴더를 되살리지 않게. 고치던 글이 있으면 닫지 않고 알린다.
  * 파일 트리 · 위키(위키 화면이고 반영이 안 돌 때) · 템플릿(템플릿 화면 · 새 업무 창일 때)도 다시 읽는다. 허브 · MOC 는
    indexSync 서명이 알아서 다시 쓴다. 파일 감시는 하지 않는다.
* **(e) 원자적 쓰기.** 새 도우미 `fsops::replace_text` — 사용자가 손으로도 고치는 파일(`index.md` 쓰기 전부 · 병합 ·
  편집기 저장 · 설정 · 템플릿 기본값)에 쓴다. 앱이 통째로 만드는 노트의 `write_atomic` · `write_if_changed` 는 그대로다
  (허브 · 위키 테스트가 그쪽 실패 동작에 기댄다).
  * 같은 폴더의 숨김 임시 파일 `.{이름}.{pid}-{n}.tmp`(`create_new`)에 쓰고, Unix 권한 · 만든 시각(Windows · macOS — 옮기지
    않으면 Obsidian 의 만든 시각 정렬이 저장마다 바뀐다)을 옮긴 뒤 `sync_all`, 이름 바꾸기. `sync_all` 을 메타데이터 뒤로
    옮겼다(계획을 바꿨다 — 함께 디스크에 내려간 뒤 바꿔 끼운다). Windows 는 오류 5 · 32 · 33 이면 20 · 50 · 100ms 로 다시
    시도한다(OneDrive · 백신).
  * **그 자리에서 쓴다(예전과 같다):** 없는 파일 · 심볼릭 링크 · 일반 파일 아님 · 쓰기로 열리지 않는 파일(바꿔 끼우면 막히던
    쓰기가 몰래 통과한다) · 하드 링크 · 숨김/시스템 속성. 임시 파일 · 이름 바꾸기가 실패해도 지우고 그 자리에서 써서 **그
    오류를 돌려준다** — 오늘 되던 쓰기가 실패로 바뀌지 않는다.
  * `write_text_file` · `reorder_tasks` · `clear_task_order` 는 블로킹 풀로 옮겼다(다시 시도 · fsync). `scan_vault` 는 동기로
    둔다 — 다시 훑기에는 차례 검사가 없어 비동기면 낡은 목록이 새 목록을 덮는다.
  * 메인 스레드의 차례가 사라져 프런트 저장을 **경로마다 한 줄**로 세운다(`saveQueue`, 버퍼는 차례가 왔을 때 읽는다). 전역
    한 줄이 아닌 까닭은 `index.md` 저장이 `metaWrite` 를 기다리는 동안 다른 노트까지 막히기 때문이다. 차례는 파일을 쓰고
    `saved` 를 맞추면 넘긴다 — `index.md` 뒤의 목록 다시 읽기까지 기다리면 카테고리 지정의 `saveAll` 과 맞물려 멈춘다
    (계획을 바꿨다). 대기 중인 저장 수 `saving` 은 다시 읽기까지 세고 (d) 가 본다. 설정의 임계값 슬라이더는 눈금마다가
    아니라 손을 뗄 때(키 · 포커스 잃음 포함) 저장한다.
* **(a) 다른 묶음 머리에 놓아 바꾸기.** 업무를 다른 묶음 **머리**에 0.3초 머물렀다 놓으면 그 카테고리로(미분류 머리면 해제).
  * **놓을 곳은 머리뿐이다.** 다른 묶음의 업무 행 사이는 전체 순서의 부분열이라 선을 그어도 그 자리를 지킬 수 없다.
  * 판정은 순수 함수 `dropKind({ at, overKey, group, armed })` → `category | reorder | cancel`. **머리 판정이 순서보다
    먼저다** — 끝 행 아래 반 행의 넘침(묶음의 맨 끝 자리)이 바로 아래 머리와 겹친다. 그래서 머물러야(`HEAD_DWELL_MS`)
    바뀌고, 그 전에 놓은 넘침은 예전처럼 맨 끝으로 옮기기다. 키는 truthiness 없이 견준다(미분류 `""`).
  * 사이드바: `TaskDrag` 에 `x` · `over { key, path, since, armed }` · `esc`. `catAt` 은 `elementFromPoint` +
    `closest("[data-cat-key]")`(목록 안만 — 밖에 놓으면 취소). `since` 는 키가 바뀔 때만 새로 잡고 자동 스크롤 뒤에도 다시
    센다. 이미 도는 50ms 타이머가 `armed` 를 켠다. 켜지면 머리를 탐색기 끌기처럼 강조하고 순서 선을 감춘다. 자기 묶음
    머리만 흐린다.
  * **Esc** 는 capture 단계 keydown 에서 `preventDefault()` 하고(겹친 창을 닫는 App 사슬이 빠진다) 끌기를 지우지 않은 채
    취소 표시만 남긴다 — 지우면 뒤따르는 click 이 그 업무를 연다.
  * 스토어 `dropOnCategory` 는 `setCategory` 길을 그대로 쓰고(정리 · 철자 맞춤 · 버퍼 보호) 칩과 달리 성공도 알린다. 토스트의
    **[되돌리기]** 는 업무가 아직 있고 값이 놓은 그대로(`keyOf`)일 때만 이전 값으로, 아니면 `그사이 바뀌어 되돌리지
    않았습니다`. 되돌리는 값도 정리 규칙을 거쳐 철자 · 손으로 접힌 셋째 단계가 그대로 돌아오지 않을 수 있다(받아들였다).
    접힌 묶음에 놓아도 펼치지 않는다.
  * 토스트 동작(새): `toast(…, { action })` — 동작이 있는 토스트만 눌리고 6초 보인다. 누르면 먼저 닫고, `done` 깃발로 한
    번만 돈다.
* **(b) 템플릿 기본 카테고리.** 템플릿 frontmatter(노트는 그 노트, 폴더는 안의 `index.md`)의 `category` 를 새 업무
  창에 미리 채운다. `TemplateMeta.category` 는 `category::read`(관대)로 읽는다.
  * **채울 뿐이다** — 업무는 칸의 값으로 만든다(`create_task` 는 템플릿의 값을 보지 않는다). `templatePrefill(지금, 앞
    기본값, 새 기본값)`: 칸이 비었거나 앞 기본값 그대로(키 비교)면 새 기본값, 손으로 고친 값은 지킨다. 템플릿을 바꿔 보는
    동안 앞 기본값이 남지도, 고른 값 · 묶음 머리 `＋` 의 카테고리가 지워지지도 않는다.
  * 정하는 곳: 등록 대화상자(두 모양 — 업무 폴더를 고르면 그 업무의 카테고리로 같은 규칙으로 채운다)와 템플릿 화면 펼친
    행(목록 틀이 `overflow: hidden` 이라 떠 있는 상자가 잘려 행 안에서 펼친다). 커맨드 `set_template_category(root, id,
    category)` 는 id 를 검사하고(`invalid`) 폴더를 먼저 찾으며(`not_found`), 쓰기 규칙으로 정규화해 같은 값이면 쓰지 않는다.
    `index.md` 없는 폴더 템플릿에는 frontmatter 만 있는 파일을 만든다.
  * `create_template_from_folder` 는 **받은 값으로 늘 덮는다** — `None` 이면 원본에서 따라온 `category:` 를 지운다. 화면에서
    고르지 않은 기본값이 보이지 않게 남지 않도록.
  * **경로 바꾸기 · 해제를 따라간다**(`retarget_templates`, 업무를 쓴 뒤). 옮기기 · 상위로 올리기는 업무와 같은
    `retarget`, 모두 미분류로는 노드 안이면 지운다 — `retarget(.., None)` 은 최상위로 올리기라 `a/x` 가 `x` 가 되므로
    규칙을 따로 받는다(계획을 바꿨다). 덤이다: 미리보기 · 합치기 판정 · `CategoryChange` 에 들지 않고, 규칙에 어긋나거나
    못 쓴 템플릿은 로그만 남긴다. [다시 시도](`only`)는 템플릿을 건드리지 않는다 — 업무와 같은 이중 이동 함정
    (`a/b/b → a/b → a`). 프런트는 성공 뒤 템플릿 목록을 다시 읽는다.
  * 카테고리 목록 · 허브에는 들지 않는다 — 목록은 업무들의 값이다(§2).
* **하지 않는 것**
  * **(f) 빈 카테고리 · 수동 순서 · 색** — 업무와 떨어진 목록 파일(레지스트리)이 있어야 한다. §1 의 사용자 결정(빈
    카테고리 · 손으로 정하는 순서를 두지 않는다)과 §2 "별도 DB · 목록 파일을 두지 않는다" 에 어긋난다. 카테고리는 붙은
    업무가 있을 때만 있고, 순서는 코드포인트 순이다.
  * **(g) 위키 페이지의 `categories` 속성** — §3 "위키 페이지에는 쓰지 않는다" 와 같은 이유다. 업무 카테고리를 바꿀
    때마다 페이지가 흔들리고 `base_hash` 비교가 반영 중인 ingest 와 부딪힌다. Obsidian 에서는 허브 노트(4단계), 앱에서는
    그때그때 센 멤버십(5단계)으로 본다.

## 6. 기존 기능과의 관계

* **이름 변경 · Archive 로 옮겨 보관 · 재개:** 값이 `index.md` 안에 있어 그대로 따라간다.
* **분할:** 새 업무가 원본 카테고리를 물려받는다(바꿀 수 있다). **병합:** 대표 업무는 자기 값을 지킨다.
  **편입:** 하위 폴더가 된 업무는 목록에서 빠지므로 개수에서도 빠진다(값은 지우지 않는다).
* **템플릿:** 기본 카테고리가 경로 바꾸기 · 해제를 따라간다(6단계 b). 템플릿에서 만든 업무는 칸에 남은 값을 쓴다.
* **Obsidian 에서 손으로 고친 값:** 앱 창에 돌아오면 다시 읽어 곧 반영된다(6단계 d) — 허브 · MOC 도 그 목록으로
  다시 쓴다. 파일을 감시하지는 않으므로 앱 창을 보는 채로 바뀐 것은 다음 계기(앱의 다음 동작 · 창에 돌아오기 ·
  재시작)에 반영된다. 앱에서 고치던 노트는 저장하면 앱 쪽이 이긴다(`index.md` 는 frontmatter 만 디스크를 따른다).
  Properties 에서는 Text 타입으로 두기를 권한다.
* **알려진 한계:** macOS 에서 붙여 넣은 자모 분리(NFD) 한글은 다른 이름이 된다. 이름을 NFD 로 돌려주는 HFS+ 에서는
  허브 파일 이름이 늘 달라 보여 갱신마다 지웠다 다시 쓴다. Dataview 는 손으로 친 원문을 비교하므로 허브의 정적
  목록이 기준이다. `index.md` · 편집기 저장 · 설정은 바꿔 끼워 쓰지만(6단계 e) 바꿔 끼운 파일은 새 파일이라 NTFS
  대체 데이터 스트림 · 그 파일에만 준 ACL · OneDrive 고정 표시를 잃는다. 링크 · 읽기 전용 · 숨김/시스템 파일과 바꿔
  끼우기가 막힌 경우는 예전처럼 그 자리에서 써서 원자적이지 않다. 다시 읽어 바뀐 노트는 편집기 커서가 끝으로 가고,
  생각 트리의 되돌리기는 바깥에서 고친 것까지 되돌릴 수 있다.

## 7. 위험과 대응

* **버퍼 되돌림** — 가장 치명적이고 눈에 안 띈다. 1단계에서 막고 회귀 테스트로 지킨다.
* **`Sidebar.tsx` 의 변경 폭** — 행 컴포넌트를 먼저 뽑고, 평면 목록 경로는 그대로, 묶기 · 드래그 범위는 순수
  함수로 테스트한다.
* **일괄 재작성(3단계)** — 미리보기, 쓰기 전 전부 검사, 같은 바이트는 쓰지 않기, `updated` 그대로, 다시 실행해도
  안전, 실패 목록과 재시도.
* **Rust · TS 규칙 어긋남** — 공유 fixture, 백엔드가 모든 쓰기를 다시 검사.
* **허브 갱신 비용 · 흔들림** — 서명으로 거르고, 모아서 한 번, 바뀐 것만 쓰기, 쓰기는 한 번에 하나.

## 8. 순서를 이렇게 잡은 이유

1. **데이터 모델이 먼저다.** 1단계에서 값이 생기고 바로 눈에 보인다. 나머지는 모두 이 값을 읽는다.
2. **2단계는 읽기만 한다.** 새 쓰기 경로 없이 화면만 바뀌어 위험이 낮다.
3. **3단계가 유일한 일괄 재작성이다.** 위험한 일을 한 단계에 모아 집중해서 테스트한다.
4. **허브(4단계)는 일괄 지정 뒤가 좋다.** 그 전에 내면 기존 Vault 에서는 거의 미분류만 보인다.
5. **5단계는 4단계와 같은 규칙(공용 fixture)을 쓴다.** 어느 카테고리에 어떤 페이지가 드는지가 앱 화면과 Obsidian 에서
   같다(보이는 방식의 차이는 5단계 '허브와 다른 곳').
