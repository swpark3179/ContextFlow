# 업무 카테고리 로드맵

진행 중 업무와 보관함 업무를 **최대 3단계 카테고리**(예: `프로젝트 › ContextFlow › UI`)로 묶고,
Obsidian 에서 **카테고리별로 위키를 보는** 기능을 단계별 구현 계획으로 정리한 문서다. 1단계(카테고리
붙이기)를 이 브랜치에서 구현했고, 나머지는 계획이다.

## 1. 요구 — 무엇을 하려는가

* 업무 하나에 카테고리 하나. 1~3단계이고 2단계짜리도 있다(예: `프로젝트 › 프로젝트명`).
* 진행 중 업무와 보관함 업무 모두에 붙이고, 그 기준으로 묶어 본다.
* Obsidian 에서 카테고리별로 위키(그 카테고리 업무에서 나온 소스 · 절차 · 주제 · 시스템 페이지)를 본다.
* 너무 복잡하지 않게. 빈 카테고리를 미리 만들거나 순서를 손으로 정하는 기능은 두지 않는다(사용자 결정).

## 2. 제약 — 설계를 정하는 것들

* **Vault 가 진실의 원천이다.** 업무 메타데이터는 `index.md` frontmatter 에만 있다. 카테고리도 거기에 둔다.
  별도 DB · 목록 파일을 두지 않는다 — 카테고리 목록은 업무들의 값에서 만들어진다(태그와 같다).
* **업무 폴더는 옮기지 않는다.** 프런트의 업무 키가 폴더 절대 경로다(활성 업무 · `uiCache` · 오늘의 한일 ·
  추천 id). `scan` 은 `Tasks/*` 와 `Archive/<연도>/*` 한 단계만 읽고, 위키 소스 페이지는 `task_path` 로
  업무 폴더를 가리킨다. 카테고리 폴더로 옮기면 이 모두가 깨진다.
* **frontmatter 는 줄 단위로만 고친다**(`frontmatter.rs`). 다른 키 · 순서 · 따옴표 · 줄바꿈은 바이트 그대로다.
  읽을 때 따옴표 없는 값의 ` #…` 를 주석으로 자르고, `quote_if_needed` 는 `#` 을 따옴표로 감싸지 않는다 —
  그래서 카테고리는 **항상 큰따옴표로** 쓴다.
* **편집기 버퍼가 frontmatter 를 되돌린다.** `index.md` 는 본문만 편집되고 저장할 때 버퍼가 들고 있던
  frontmatter 로 파일을 다시 조립한다(`EditorPane`). 이미 열린 버퍼는 다시 읽지 않는다(`openFile`).
  백엔드가 frontmatter 를 고친 뒤 버퍼를 맞추지 않으면 다음 타이핑이 카테고리를 지운다.
* **위키 페이지는 모델이 본문을, 앱이 경로 · frontmatter · 색인을 소유한다.** 위키 페이지에 카테고리를
  써 넣으면 이름을 바꿀 때마다 페이지가 흔들리고 `base_hash` 비교가 반영 중인 ingest 와 부딪힌다.
* **Obsidian 사용자는 Dataview 가 없을 수도 있다.** 카테고리별 보기는 플러그인 없이 읽혀야 한다.

## 3. 핵심 결정

| 주제 | 결정 | 이유 |
| --- | --- | --- |
| 저장 | `index.md` 의 `category: "프로젝트/ContextFlow/UI"` 한 키. 미분류면 키가 없다 | Obsidian Properties 에 Text 로 그대로 보인다 |
| 개수 | 업무당 하나(경로 1~3단계). 여러 곳에 걸치는 꼬리표는 기존 `tags` | 트리 · 개수 · 드래그가 단순하다 |
| 정리 규칙 | `/` · `\` · `›` 로 나눈다. 단계마다 `: * ? " < > \| # ^ [ ] ,` 와 제어 문자 → `-`, 공백 접기, 앞뒤 공백 · 점 제거, 30자 자르기, 빈 단계 버리기. 쓸 때 4단계 이상 · `미분류/…` 는 거절 | 파일 이름 규칙(`sanitize_name`)과 같은 선례. 허브 노트의 위키링크가 깨지지 않는다 |
| 손편집 | 읽을 때는 관대하다: 따옴표 없음 · 목록형(첫 항목) · 4단계 이상(셋째 단계에 ` · ` 로 접음) | Obsidian 에서 고친 값도 잃지 않는다. 앱이 그 업무를 다음에 쓸 때 정규형이 된다 |
| 같음 · 순서 | 비교는 소문자 경로로. 표시는 가장 많이 쓰인 철자. 형제는 코드포인트 순(한글은 가나다), 미분류는 맨 끝 | Windows 에서 대소문자만 다른 허브 파일이 생기지 않는다. Rust 와 TS 의 순서가 같다 |
| 부수효과 | 카테고리를 바꿔도 `updated` · `order` 는 그대로, Run Log · 오늘의 한일에 남기지 않는다 | 정리는 작업이 아니다(순서 바꾸기와 같은 규칙). 위키 `source_sig` 는 본문만 보므로 stale 이 되지 않는다 |
| 규칙 공유 | `src/lib/category.cases.json` 하나를 Rust(`include_str!`)와 TS 테스트가 함께 읽는다 | 화면이 받아 준 값을 백엔드가 거절하는 일이 없다 |
| Obsidian 보기 | 앱이 만드는 허브 노트 `_index/카테고리.md` · `_index/카테고리/카테고리 · 프로젝트 › ContextFlow.md` | `_index/` 는 이미 앱 몫(보관함 MOC). 접두어로 위키 페이지와 이름이 겹치지 않는다 |
| 위키 ↔ 카테고리 | 위키 페이지에는 쓰지 않는다. 소스 페이지는 `task_id`, 나머지는 `sources` 업무들의 카테고리로 그때그때 계산 | 페이지가 흔들리지 않고 ingest 와 충돌하지 않는다 |

## 4. 데이터 모델

```yaml
---
id: task-2026-1002-093000
title: 대시보드 개편
status: in-progress
tags: [UI]
category: "프로젝트/ContextFlow"
created: 2026-10-02 09:30
...
---
```

* `create_task` 는 `tags` 바로 뒤에 쓴다. 기존 노트에 처음 붙일 때도 `tags` 뒤에 끼우고, 이후엔 제자리에서
  고친다. 해제하면 키를 지운다.
* Rust `category.rs`: `normalize(값, 쓰기|읽기)` · `read(&Doc)` · `write(&mut Doc, 값)` · `set_category`.
  `TaskMeta.category: Option<String>`, `NewTask` · `SplitTask` 에 `category`.
* 커맨드 `set_task_category(root, folders, category)` → `{ tasks, changed, failed }`. 여러 업무를 한 번에
  받는다(3단계의 일괄 지정이 그대로 쓴다). 같은 값이면 파일을 다시 쓰지 않는다.
* TS `src/lib/category.ts`: `normalizeCategory` · `label`(`프로젝트 › ContextFlow`) · 카테고리 목록 · 추천.

## 5. 단계별 계획

### 1단계 — 카테고리 붙이기 (이 브랜치)

* **보이는 것:** 워크스페이스 머리글 둘째 줄 맨 앞에 칩(`프로젝트 › ContextFlow ▾`, 없으면 `＋ 카테고리`) →
  누르면 고르는 상자. 새 업무 · 업무 분할(원본 값을 미리 채움)에 카테고리 칸. 유사 업무 추천이 같은 카테고리를
  가리키면 한 번에 고르는 제안. 사이드바 행 · 보관함 카드에 흐린 라벨, 검색이 카테고리도 맞춘다.
  보관함 상세에서도 바꿀 수 있다.
* **고르는 상자(`CategoryPicker`):** 입력 + 바로 아래 펼쳐지는 목록. ↑↓ 로 고르고 Enter(한글 조합 중 Enter 는
  무시), Tab 은 고른 경로 뒤에 `/` 를 붙여 하위로 내려가기, Esc 는 닫기. `미분류 (카테고리 없음)` 과
  `＋ 새로 만들기` 줄, 실제로 저장될 값 미리보기.
* **버퍼 보호:** 백엔드가 `index.md` 를 고친 뒤 깨끗한 버퍼는 디스크 내용으로 바꾸고, 고치던 버퍼는 본문을
  그대로 둔 채 frontmatter 만 디스크 것으로 맞춘다. 같은 문제가 있던 보류 · 재개 · 이름 변경 · 분할(원본)과
  스냅샷에서 되살린 버퍼에도 적용한다.
* **완료 조건:** 지정 직후 `index.md` 를 타이핑해도 카테고리가 남는다. 재시작해도 남는다. Obsidian 에서
  `updated` 가 그대로다. 보관 업무의 위키 상태가 fresh 로 남는다.

### 2단계 — 카테고리로 묶어 보기 (업무 리스트 트리 · 보관함 필터)

* **보이는 것:** 진행 중 업무에 카테고리가 하나라도 있으면 업무 리스트가 접히는 트리가 된다
  (`▼ 프로젝트 5 › ▼ ContextFlow 3 › ● 업무`). 미분류는 맨 끝. 접힌 상태는 재시작 뒤에도 남는다. 상태
  필터 · 검색은 개수를 다시 세고 빈 묶음을 숨기며, 검색 중에는 모두 펼친다. 머리글 메뉴에 묶어 보기 끄기 ·
  모두 접기 · 모두 펼치기. 묶음 머리 `＋` 로 그 카테고리의 새 업무.
* **보관함:** `카테고리` 선택(전체 · 들여쓴 트리와 개수 · 미분류)으로 하위까지 거른다. `묶기: 분기 | 카테고리`.
  카드의 카테고리 칩을 누르면 그 카테고리로 거른다.
* **드래그:** 같은 묶음 안에서만 순서를 바꾼다. 묶음의 행은 전체 순서의 부분열이라 `reorderedList` 를 그대로
  쓴다. 다른 묶음으로 끌어 카테고리를 바꾸는 것은 실수하기 쉬워 6단계로 미룬다.
* **구현:** 순수 함수 `buildCategoryTree` · `flattenSideRows` · `groupArchived` 에 규칙을 두고 테스트한다.
  `Sidebar.tsx` 는 행을 `TaskRow` 로 뽑고 `CategoryRow` 를 더하되, 카테고리가 없을 때의 평면 목록 경로는
  그대로 둔다. 백엔드 변경 없음.

### 3단계 — 카테고리 관리 (일괄 지정 · 경로 바꾸기 · 해제)

* **보이는 것:** `카테고리 관리` 대화상자. 왼쪽 트리(진행 n · 보관 m, 처음엔 미분류), 오른쪽 그 노드의 업무
  목록(체크 · Shift 범위 선택 · 검색 · `진행 중만 | 보관 포함`), 아래 [카테고리 지정]. 쌓인 업무를 몇 번에
  정리할 수 있다.
* **노드 동작:** [경로 바꾸기] — 이름 바꾸기 · 상위 옮기기 · 합치기가 모두 "앞부분 바꾸기" 하나다. 바뀔 업무
  수를 미리 보이고, 대상이 이미 있으면 [합치기] 확인을 받는다. [해제] — 상위로 올리거나 미분류로.
* **구현:** 커맨드 `move_category(root, from, to, allow_merge)`. 쓰기 전에 전부 검사한다(4단계 넘침 · 자기
  하위로 옮기기 거절). 업무마다 파일의 **지금 값**으로 다시 계산하므로 다시 실행해도 안전하고, 그사이
  Obsidian 에서 바뀐 노트는 건너뛴다. 잠긴 파일은 실패 목록으로 알리고 [다시 시도].

### 4단계 — Obsidian 에서 카테고리별로 보기 (허브 노트 · 보관함 MOC 고침)

* **허브 노트(플러그인 없이 읽힌다):**
  * `_index/카테고리.md` — 전체 트리, 줄마다 하위 허브 링크와 `업무 12 (진행 3) · 위키 9`.
  * `_index/카테고리/카테고리 · 프로젝트 › ContextFlow.md` — 노드마다 하나(중간 노드 포함). 하위 카테고리 ·
    진행 중 업무 · 완료 · 보관 업무(위키 소스 페이지로 링크, 아직 없으면 업무 노트로 링크 + "위키 반영 전") ·
    그 업무들에서 나온 위키 페이지(절차 · 주제 · 시스템 · 질의 답변). 하위 카테고리까지 합쳐 보인다.
  * `카테고리 · 미분류.md` — 정리할 목록을 겸한다. `Wiki/index.md` 에 허브로 가는 한 줄.
* **규칙:** 바이트가 고정된다(시각 · `updated` · 회차를 넣지 않고, 바뀐 경우에만 쓴다). 업무 링크는 `[YYYY-MM]`
  괄호 때문에 위키링크 대신 인코딩한 마크다운 링크(위키 소스 페이지 꼬리말과 같은 방식). 앱이 만든 표식
  (`type: category-hub`, `generator: contextflow`)이 있는 파일만 지우고, 같은 자리에 사용자 파일이 있으면
  건드리지 않고 알린다. Dataview 표는 ContextFlow 폴더가 곧 Obsidian vault 일 때만 접어서 덧붙인다.
* **갱신 시점:** 업무 목록의 (폴더 · 제목 · 상태 · 보관 · 완료일 · 카테고리) 서명이 바뀌면 잠깐 모았다가 쓴다.
  위키 반영이 도는 동안은 미루고 끝나면 쓴다. 지금 보관함 MOC 갱신은 새 업무 · 분할 · 기록 후 삭제에서 불리지
  않으니, 호출 지점을 늘리는 대신 서명 구독으로 간다. 설정에서 끌 수 있다.
* **보관함 MOC 고침(`_index/Archive.md`):** `Archive/` 로 옮긴 업무가 빠지던 Dataview 범위, `reference/` 사본이
  겹쳐 세지던 문제, `[YYYY-MM]` 폴더라 깨지던 링크, 셀의 `|`, 갱신할 때마다 바뀌던 "최종 갱신" 시각.
  카테고리 열을 더한다.
* **앱에서 열기:** 묶음 머리 메뉴 · 관리 대화상자 · 보관함 묶음 머리의 `Obsidian에서 보기`. macOS · Linux 는
  탐색기 열기로 대신하고, `Tasks/` 만 vault 로 등록했다면 `_index/` 는 열 수 없다(문서에 적는다).

### 5단계 — 앱 위키 화면에서도 카테고리별로 · 반영 프롬프트에 카테고리

* 위키 화면 왼쪽에 `카테고리` 선택 → 유형별 목록 · 개수 · 검색 결과를 그 카테고리 페이지로 좁힌다. 허브와
  같은 계산을 쓰므로 목록이 똑같다. Obsidian 버튼은 그 허브를 연다. 페이지 패널에 카테고리 칩.
* 새로 반영할 때 모델이 `카테고리: 프로젝트 › ContextFlow` 를 보고, 관련 페이지 검색어에 카테고리 이름을 더한다.
* 구현: `wiki::status` 가 페이지마다 카테고리를 계산해 실어 준다(파일에 쓰지 않는다).

### 6단계 — (선택) 있으면 좋은 것들

* (a) 다른 묶음으로 끌어 놓아 카테고리 바꾸기 · (b) 템플릿의 기본 카테고리 · (c) `AI에게 묻기` 를 한
  카테고리 안으로 한정 · (d) 창에 돌아올 때 다시 읽기(Obsidian 손편집 즉시 반영) · (e) `index.md` 원자적 쓰기 ·
  (f) 빈 카테고리 · 수동 순서 · 색(목록 파일) · (g) 위키 페이지에 Dataview 용 `categories` 속성.
* 데이터 모델을 바꾸지 않고 하나씩 더할 수 있다.

## 6. 기존 기능과의 관계

* **이름 변경 · Archive 로 옮겨 보관 · 재개:** 값이 `index.md` 안에 있어 그대로 따라간다.
* **분할:** 새 업무가 원본 카테고리를 물려받는다(바꿀 수 있다). **병합:** 대표 업무는 자기 값을 지킨다.
  **편입:** 하위 폴더가 된 업무는 목록에서 빠지므로 개수에서도 빠진다(값은 지우지 않는다).
* **Obsidian 에서 손으로 고친 값:** 다음에 다시 읽을 때(앱의 다음 동작 · 재시작) 반영된다. Properties 에서는
  Text 타입으로 두기를 권한다.
* **알려진 한계:** macOS 에서 붙여 넣은 자모 분리(NFD) 한글은 다른 이름이 된다. Dataview 는 손으로 친 원문을
  비교하므로 허브의 정적 목록이 기준이다. `index.md` 쓰기는 원자적이지 않다(6단계 e).

## 7. 위험과 대응

* **버퍼 되돌림** — 가장 치명적이고 눈에 안 띈다. 1단계에서 막고 회귀 테스트로 지킨다.
* **`Sidebar.tsx` 의 변경 폭** — 행 컴포넌트를 먼저 뽑고, 평면 목록 경로는 그대로, 묶기 · 드래그 범위는 순수
  함수로 테스트한다.
* **일괄 재작성(3단계)** — 미리보기, 쓰기 전 전부 검사, 같은 바이트는 쓰지 않기, `updated` 그대로, 다시 실행해도
  안전, 실패 목록과 재시도.
* **Rust · TS 규칙 어긋남** — 공유 fixture, 백엔드가 모든 쓰기를 다시 검사.
* **허브 갱신 비용 · 흔들림** — 서명으로 거르고, 모아서 한 번, 바뀐 것만 쓰기, 쓰기는 한 번에 하나.

## 8. 순서를 이렇게 잡은 이유

1. **데이터 모델이 먼저다.** 1단계에서 값이 생기고 바로 눈에 보인다. 나머지는 모두 이 값을 읽는다.
2. **2단계는 읽기만 한다.** 새 쓰기 경로 없이 화면만 바뀌어 위험이 낮다.
3. **3단계가 유일한 일괄 재작성이다.** 위험한 일을 한 단계에 모아 집중해서 테스트한다.
4. **허브(4단계)는 일괄 지정 뒤가 좋다.** 그 전에 내면 기존 Vault 에서는 거의 미분류만 보인다.
5. **5 · 6단계는 4단계의 계산을 그대로 쓴다.** 앱 화면과 Obsidian 이 같은 목록을 보인다.
