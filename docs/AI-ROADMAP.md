# 업무 이력 AI 적용 로드맵

ContextFlow 가 쌓는 업무 이력에 AI 를 어디에 더 쓸 수 있는지 검토하고, 단계별 구현 계획으로 정리한
문서다. 0단계(AI 설정 완성 · LLM 위키)를 구현했고, 3단계의 L(다중 턴)과 새 항목 Q(웹 검색)를 앞당겨
구현했다. 새 항목 R(위키 가이드) · S(간략 입력 정리)도 구현했다. 나머지는 계획이다.

## 1. 쓸 수 있는 재료 — 이 앱이 이미 가진 업무 이력

| 재료 | 어디에 | 무엇이 들었나 | AI 에게 주는 가치 |
| --- | --- | --- | --- |
| 업무 폴더 | `Tasks/` · `Archive/[연도]/` | `index.md`(frontmatter 메타 · 개요 · 체크리스트 · Run Log), 첨부, 메모 | 한 일의 원문 — 요약 · 절차 추출의 원천 |
| Run Log | 각 `index.md` 의 `## 실행 이력 (Run Log)` | 회차별 한 줄(생성 · 재개 · 편입 · 분할 · 병합) | 업무의 시간축 — "어디까지 했나" |
| 오늘의 한일 | `~/.contextflow/today.db` (SQLite) | 날짜 · 업무 · 시각 · 손으로 넣은 회의/전화 기록 | 날짜로 묻는 질문 — 일/주/월간 보고 |

## 2. 제약 — 설계를 정하는 것들

* **연결 3종(FabriX · Claude Code · Codex CLI)의 공통 분모는 텍스트 스트림이다.** AI Pro 는 걷어 냈다.
  로컬 CLI 는 도구를 막고 돌리고, FabriX 채팅 API 는
  tool calling 이 없다. 그래서 기본 패턴은 "앱이 재료를 골라 프롬프트에 싣고 → 정해진 형식(펜스 JSON ·
  구분자 블록)으로 받아 → 앱이 쓴다" 이다. tool calling 은 FabriX **LLM 게이트웨이**(OpenAI 호환)에서만
  가능하다 — 그것을 쓰는 기능은 게이트웨이를 고른 경우로 한정한다(3단계).
* **사내망 · 개인정보.** 업무 내용이 고른 연결로 나간다. 기능별 연결로 민감한 일은 사내 연결에만 맡기게
  했지만, 전송 전 마스킹은 아직 없다(4단계).
* **추론 모델은 생각 토큰도 출력 상한에 센다**(사내 GLM 에서 확인). 긴 출력을 받는 기능은 상한을
  넉넉히 잡고, 잘림을 형식 위반과 구별해 알린다.
* **Vault 가 진실의 원천이다.** AI 가 만든 것도 Obsidian 에서 보이는 마크다운으로 남기고, 사람이 쓴 것은
  덮어쓰지 않는다(위키의 해시 비교 · 덧붙이기 · `.history` 규칙을 다른 기능에도 쓴다).

## 4. 단계별 계획

### 0단계 — AI 설정 완성 · LLM 위키 (완료, 이 브랜치)

* FabriX 두 방식(채팅 API · LLM 게이트웨이), 모델 이름→id 해석, 사용자 이메일, 직접 지정 모델, 2단계
  연결 테스트, 실제 응답 모양(THINK · FR-201) 대응, 스트림 유휴 상한 명시.
* 기능별 AI 연결(기본 · 위키 반영 · 위키 질의/점검)과 [테스트] 대화, 추천 실패 사유 표시, 프롬프트 팩
  지점(추천 · 위키 반영 · 질의 · 점검)과 순서.
* LLM 위키: 완료 시 자동 반영(뒤에서 · 큐), 일괄 반영, 위키 화면(검색 · 페이지 · 링크 · 원본 업무 열기 ·
  AI에게 묻기 · 답변 저장 · 점검), `Wiki/` 저장소(SCHEMA · index · log · .history).
* 사내 FabriX 채팅 API 로 끝까지 돌려 확인했다(README "LLM 위키" · "알려진 제약").

### 앞당겨 한 것 — 대화 · 웹 검색 (L · Q)

* **L. 이어서 묻기** — 위키 질의를 대화로 바꿨다. 이력은 `RunArgs.history` 대신 **프롬프트에 접어** 보낸다
  (`lib/wiki/prompts.ts` 의 `historyBlock`). 계획에서는 FabriX `contents` 배열 · 게이트웨이 `messages` 로 나눠
  보내려 했지만, 세 연결이 같은 방식으로 돌고 위키 페이지 본문을 턴마다 다시 고를 수 있어(이력에는 질문과 답만)
  이쪽이 단순하고 싸다. 대화는 하나만, 위키 화면에 있는 동안만 이어지고 [대화 초기화] 가 있다. 이어지는 질문은
  앞선 질문과 합친 검색 · 앞선 인용 페이지로 페이지를 고른다(`pickContextPages`).
* **Q. 웹 검색** — 위키 질의 중 AI 가 PC 의 Chrome · Edge 를 DevTools 프로토콜로 조종해 검색하고 결과 페이지
  본문을 읽는다(`src-tauri/src/browser.rs`). 도구 호출이 없는 연결에서도 되도록 ` ```websearch ` 펜스라는 글로 된
  약속을 쓰고, 읽은 페이지는 기능별 연결 **웹 검색**으로 따로 고른 모델이 `[웹n]` 출처 붙은 사실로 줄인 뒤 질의
  모델에 넘긴다(`lib/wiki/web.ts`). 질문 하나에 검색 두 번까지. 브라우저는 전용 프로필로 띄우고 검색 결과 읽기 ·
  본문 읽기만 한다.
* 남은 일: 실제 검색 엔진(사내 PC)에서 결과 모양 확인(`live_engines` 테스트), 검색어 마스킹(N 과 함께), J 의
  도구(위키 검색 · 페이지 읽기)도 같은 글 약속으로 열 수 있는지 — 게이트웨이 전용 tool calling 보다 넓게 쓰인다.

### 앞당겨 한 것 — 업무 AI 도우미 (R · S · T)

워크스페이스 머리의 [✦ AI ▾] 에서 지금 업무에 대해 부른다(README "업무 AI 도우미").

* **R. 위키 가이드** — 업무 자체(제목 · 태그 · 카테고리 · 개요)로 위키를 찾아 요약 · 진행 순서 · 주의할 점 ·
  미리 확인할 것 · 참고할 위키를 쓴다. 저장하면 `AI 가이드.md` 에 날짜 머리로 덧붙이고, 아니면 버린다. 1단계 C(새
  업무 대화상자의 관련 위키)의 "이 절차로 시작" 을 이미 있는 업무에서 하는 셈이다. B(재개 브리핑)와 달리 사람이
  부를 때만 돈다.
* **S. 간략 입력 정리** — 한두 줄 메모를 정리해 알맞은 파일 · 섹션에 덧붙인다. 요구사항은 개요 · 할 일 · 일정 · 관련 ·
  확인 필요로, 끝낸 일은 맞는 열린 할 일의 체크와 `진행 기록` 한 줄로, 상황은 그 일을 다루는 파일의 기록 한 줄로.
  항목마다 근거 id 를 받아 근거 없는 것은 앱이 버리고, 빠진 것은 선택지 · 입력으로 되묻는다(최대 3바퀴). 3단계 J 가
  계획한 "사람 승인 뒤에만 쓰기" 를 도구 호출 없이 먼저 한 것이다 — 파일별 미리보기에서 빼고 옮긴 뒤 → [쓰기].
* **T. 이슈 추가** — 업무 중 새로 생긴 일 · 테스트 회신 · 문제를 짧게 적으면 사실만으로 정리하고(근거 id, 되묻지
  않고 빠진 것은 확인 필요로), 이 이슈를 처리할 새 파일(`이슈/날짜 제목.md`)을 만들거나 기존 파일의 섹션 끝에 한
  건으로 넣고 그 자리를 연다. 쓸 곳은 후보 파일 · 제목의 id 로만 고르게 해 앱이 검증하고, 사람이 바꾼 뒤 쓴다.
  index.md 의 `## 이슈` 에 한 줄을 남겨 열린 이슈가 업무의 중심 문서에서 보인다.
* 셋 다 기능별 연결(`task.guide` · `task.brief` · `task.issue`)과 프롬프트 팩 지점을 따로 둔다. 쓰기는 새 커맨드 없이
  편집기와 같은 길(버퍼에 얹고 저장)이라 고치던 글이 지워지지 않는다.
* 남은 일: 가이드의 인용 칩에서 위키 페이지 열기(저장하지 않은 가이드를 잃지 않게 — 저장 뒤 열기), 정리본을 팝업
  안에서 고치기, 새 업무 대화상자에서 바로 정리하기(만들면서 개요 · 할 일을 채우기).

### 1단계 — 위키를 일하는 자리로 끌어오기 (작은 것 셋)

목표: 위키를 "보러 가는 곳" 에서 "일하다 저절로 만나는 곳" 으로.

**B. 재개 브리핑**
* 언제: 보류 · 재개한 업무를 열 때, 또는 마지막 손댄 지 N일(설정, 기본 7일) 지난 업무를 열 때.
* 재료: Run Log 최근 10줄 · 스냅샷의 열린 탭과 메모장 · 오늘의 한일에서 그 업무의 날짜들 · 최근 수정
  파일 5개의 앞부분 · 그 업무와 관련된 위키 페이지(로컬 검색 상위 3).
* 출력: 자유 마크다운 5줄 이내("마지막으로 한 일 · 남은 일 · 참고할 위키") → 워크스페이스 머리에 접을
  수 있는 띠로. 파일에는 쓰지 않는다(읽고 버리는 정보).
* 구현: `src/lib/briefing.ts`(프롬프트 · 조립, 순수), `routes` 에 `briefing` 추가(기본 연결 따름),
  `useStore.selectTask` 뒤에 비동기 호출 · 업무별 캐시(내용 서명이 같으면 다시 묻지 않는다).
* 완료 조건: 오프라인 · 연결 없음이면 띠가 아예 안 뜬다. 응답이 늦어도 업무 열기를 막지 않는다.

**C. 새 업무 대화상자의 관련 위키**
* 지금 대화상자는 유사 업무(로컬 · AI)를 추천한다. 그 아래에 `wiki_search(제목 + 개요)` 상위 3장을
  "관련 절차 · 시스템" 으로 붙인다 — 네트워크 없이 즉시.
* [이 절차로 시작] → 절차 페이지의 번호 목록을 새 업무 `index.md` 의 체크리스트로 넣는다(사람이 고칠
  수 있는 초안). 출처 위키링크를 함께 남긴다.
* 구현: `NewTaskModal.tsx` 에 카드 한 줄, `vault::create_task` 의 summary 에 체크리스트를 이어 붙이는
  경로(새 커맨드 없이 개요 텍스트로).

**D. 완료 회고 초안**
* [완료] 직전에 "이번에 배운 것 3줄" 초안을 제안하고, 받아들이면 Run Log 에 회고 한 줄로 남긴다.
* 위키 반영의 품질이 오른다(원본에 결론이 적혀 있으면 소스 페이지의 "결정과 이유" 가 정확해진다).
* 설정으로 끌 수 있고 기본은 끔(완료 흐름에 대화상자를 하나 더 끼우는 것이라).

### 2단계 — 시간축과 반복 패턴

**E. 일 · 주 · 월간 보고서**
* 커맨드: `daylog::day_range(from, to, vault)` 신설(지금은 날짜 하나씩만 읽는다).
* 재료: 기간의 오늘의 한일 + 그 업무들의 위키 소스 페이지 요약(없으면 index.md 개요).
* 출력: `Reports/2026-W40.md`(Vault 안, Obsidian 에서 보인다) — "한 일 · 진행 중 · 다음 주" 섹션,
  업무마다 소스 페이지 링크. 같은 기간을 다시 만들면 `.history` 에 이전본을 남기고 덮는다.
* 화면: 오늘의 한일 팝업에 [이번 주 보고서] 버튼.

**F. 반복 업무 → 표준 패턴 초안**
* 위키 점검에 "같은 절차 페이지를 근거로 둔 업무가 3건 이상" 규칙을 더하고, 그 절차를
  `Templates/<이름>.md` 초안으로 만드는 [템플릿으로] 버튼을 단다(체크리스트 + Run Log 섹션).
* 기존 "생성하지 않은 중복 노트" 수치(템플릿 화면)와 연결해, 템플릿이 실제로 아낀 것을 보인다.

**G. 자동 태깅 · 제목 정리** — 위키 반영 계획의 `tags` 를 업무 frontmatter 에 **제안**(사람이 수락)하고,
Vault 전체 태그를 정규화하는 점검 규칙(대소문자 · 동의어). 업무 `index.md` 는 줄 단위 편집만 쓴다.

**H. 브레인스토밍 확장 제안** — 고른 노드에 대해 "뻗어 볼 하위 생각 3개 · 근거/리스크" 를 제안하고,
받아들인 것만 `.bs.md` 에 탐색중 노드로 넣는다. 관련 위키 페이지를 근거 필드에 인용한다.

**I. 생성 파라미터 UI** — 연결별 접는 "고급" 섹션(온도 · top_p · FabriX 의 top_k · repetition_penalty ·
seed). 기능별 기본 온도(추천 0.4 · 위키 0.2)는 코드에 두고, 설정 값이 있으면 그것이 이긴다.

### 3단계 — 도구를 쓰는 AI (게이트웨이 · 로컬 CLI)

**J. 위키 기반 대화형 에이전트**
* FabriX LLM 게이트웨이의 OpenAI tool calling(바탕화면 FabrixSample 의 `sample_agent_loop` ·
  `sample_mcp_tools`)을 쓴다. 도구: `wiki_search` · `wiki_read_page` · `task_search` · `task_read_file` ·
  `draft_checklist`(쓰기 초안).
* **쓰기는 사람 승인 뒤에만**(샘플의 `sample_graph_interrupt` — Outline → Draft → Review). 에이전트는
  초안을 만들고, 화면이 diff 를 보여 주고, 사용자가 [적용] 을 눌러야 파일이 바뀐다.
* 루프 상한(예: 8단계) · 도구 호출 로그를 위키 log.md 에 남긴다.
* 구현: Rust 에 `agent_loop`(게이트웨이 전용, `RunArgs` 에 `tools` · `messages` 추가), 프런트에 대화 패널.

**K. MCP 서버 노출** — `contextflow-mcp`(stdio)로 위키 검색 · 페이지 읽기 · 업무 검색을 내보내, Claude
Code/Codex 에서 "내 위키에서 QA 롤백 절차 찾아 줘" 가 되게 한다. 읽기 전용부터 시작한다.

**L. 다중 턴** — 완료(위 "앞당겨 한 것"). 계획과 달리 이력을 프롬프트에 접어 보낸다.

### 4단계 — 보안 · 운영

**M. 자격 증명 OS 보관** — Windows 자격 증명 관리자(`keyring` 크레이트)에 토큰을 두고 ai.json 에는 참조만.
첫 실행에서 평문을 옮기고 지운다(실패하면 평문 유지 + 경고). 다른 PC 로 옮길 때 다시 입력해야 한다는
점을 설정 화면에 적는다.

**N. 전송 전 마스킹** — 프롬프트를 보내기 직전 정규식 마스킹(주민등록번호 · 휴대전화 · 이메일 · 사번 ·
`password=` · 토큰 모양 문자열) → `‹마스킹:전화›`. 연결별로 켜고 끄며(사내 연결은 끌 수 있게), 위키 반영
번들에는 기본 적용. 마스킹 건수를 log.md 에 남긴다.

**O. 사용량 대시보드** — 이미 오는 `usage` 이벤트를 `~/.contextflow/usage.db` 에 기능 · 연결 · 모델별로
쌓고 설정 화면에 월간 합계.

**P. 임베딩 검색** — 사내 임베딩 API 가 확보되면 위키 페이지 임베딩을 `Wiki/.index/` 에 두고 로컬 검색과
섞는다(BM25 + 벡터). 그 전까지는 지금의 IDF 검색과 색인(index.md)으로 충분하다(수백 장 규모).

## 5. 순서를 이렇게 잡은 이유

1. **0단계가 나머지의 바닥이다.** 재개 브리핑 · 보고서 · 에이전트 모두 "이미 정리된 지식" 이 있을 때
   싸고 정확해진다. 원본을 매번 다시 읽히는 대신 위키를 1차 근거로 쓴다.
2. **1단계는 새 저장소 없이 화면 몇 군데만 고친다.** 위험이 낮고, 위키가 일상 흐름에 들어와 쌓이는 속도가
   빨라진다(쓰면 쌓이고, 쌓이면 쓸모가 커진다).
3. **2단계는 새 커맨드(`day_range`)와 새 산출물(Reports · Templates 초안)이 생긴다.** 1단계에서 프롬프트 ·
   형식 규약이 안정된 뒤가 좋다.
4. **3단계는 연결이 게이트웨이로 한정되고 쓰기 권한 설계가 필요하다.** 사람 승인 흐름을 먼저 정하고 들어간다.
5. **4단계의 M · N 은 사용자가 늘면 앞당긴다.** 지금은 기능별 연결로 "어느 서비스로 나가는지" 를 사용자가
   고르게 해 두었다.
